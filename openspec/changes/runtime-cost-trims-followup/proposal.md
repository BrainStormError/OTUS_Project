## Why

Замер на стенде: `SELECT count(*) FROM ratings` по 11 строкам занимает 250–360 мс в первой сессии psql и 1–4 мс в последующих; TTFB страницы ~726 мс; `vmstat` показывает `r = 7–12` при `nproc = 1`. Тёплые запросы стоят 1–4 мс — база в порядке, данных мало. Упираемся в одно ядро: процессорное время делят Next.js, Postgres и обслуживание кэша TMDB.

Главный претендент на краденое ядро — обслуживание кэша. `sweepExpiredIfDue` запускается прямо из `readThrough`, то есть в запросе пользователя. Вытеснение считает оконную сумму `SUM(payload_bytes) OVER (ORDER BY updated_at, id)` по всей таблице, которая по бюджету может быть в 100 МБ — больше, чем `shared_buffers=64MB`. Проверка TTL читает весь `payload`, чтобы понять, истёк ли он. Планировщик Postgres при этом вслепую: `n_live_tup = 0` во всех таблицах, `last_autovacuum` пуст почти везде.

## What Changes

- **Обслуживание кэша уходит из запроса.** Sweep перестаёт запускаться из `readThrough` и переходит на фоновый таймер с ограниченной частотой. Рендер страницы больше не конкурирует с обслуживанием кэша за ядро.
- **Вытеснение ограничено объёмом работы, а не размером кэша.** Вместо оконной суммы по всей таблице — обход по индексу `updated_at` с остановкой, как только набран нужный объём байт. Стоимость вытеснения перестаёт расти вместе с кэшем.
- **Проверка TTL не читает `payload`.** Попадание в кэш сверяет срок по `expires_at` и поднимает `payload` только для свежей записи.
- **Планировщик получает статистику.** `VACUUM ANALYZE` включается в шаг деплоя после миграций — сейчас статистики нет ни по одной таблице.
- **Не меняется.** Бюджет кэша (100 МБ) и параметры Postgres (`shared_buffers=64MB`, `work_mem=4MB`, `max_connections=20`) остаются ровно как в `platform/resource-budgets`. Пересмотр чисел — отдельное решение, и принимать его надо по замеру после этой правки, а не до.

### Modified Capabilities

- `platform/resource-budgets`: добавляется требование о стоимости обслуживания кэша — очистка и вытеснение не выполняются в пути запроса, а объём работы вытеснения ограничен целью по байтам, а не размером таблицы.
- `platform/data-access`: добавляется требование об актуальной статистике планировщика — деплой обновляет её, чтобы планы не выбирались по пустой оценке кардинальности.

## Impact

- **Code:** `src/modules/catalog/service.ts` — sweep на фоновом таймере вместо вызова из `readThrough`; `src/modules/catalog/cache-repository.ts` — вытеснение обходом по индексу `updated_at` с ранней остановкой вместо оконной суммы по всей таблице; проверка TTL отдельно от чтения `payload`.
- **Infra:** `scripts/deploy.sh` — шаг `VACUUM ANALYZE` после миграций, до старта приложения.
- **Tests:** unit — стоимость вытеснения не зависит от числа строк в кэше (остановка по набранному объёму), проверка TTL не читает `payload`, sweep не запускается из пути запроса; интеграционные — порядок вытеснения сохранён (самые старые по `updated_at` уходят первыми), бюджет соблюдается, просроченные записи убираются и без превышения бюджета.
- **Координируется с:** change `runtime-cost-trims` (его нужно заархивировать первым — он уже в работе и требует `navigation-performance` перед собой) и change `static-shell` (второй change из этого решения; независим от этого по коду, но его эффект виден только после того, как ядро освободится).
