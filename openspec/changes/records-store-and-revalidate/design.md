## Context

См. `proposal.md` — Why. Текущее состояние (из разведки кода):

- `useWatchedRecords` и `useWatchlist` — хуки с локальным `useState`, сид из RSC-пропсов, сверка по «подписи» содержимого (`record-store.ts:26-33`, `watchlist-store.ts:30-37`). Каждый экран создаёт свой экземпляр.
- Главная читает записи через `listWatchedRecords` (`listPersonalRatings`), `/films` — через `listCatalog` (`listRatedTitles`); оба читают одни и те же строки `ratings` (`group_id IS NULL`), но разными запросами и адаптерами.
- После мутации вызывается `router.refresh()` (`record-store.ts:65,80`). В Next 16.3.8 refresh инвалидирует сегментный кэш и перезапрашивает текущий маршрут, но ответ навигации, начатый до коммита мутации, может перезаписать свежие данные (в `upsertSegmentEntry` есть соответствующий `TODO`).
- `next.config.js` задаёт `experimental.staleTimes.dynamic: 30`, ссылки оболочки — с `prefetch` (`nav-links.tsx:55`): пустой снапшот раздела живёт в клиентском Router Cache до 30 c.
- При ошибке мутации оптимистичное изменение не откатывается (`record-store.ts:56-58,81-85`); в `watchlist-store.ts:51,62` откат есть.

## Goals / Non-Goals

**Goals:**
- Личные списки (просмотренное и «Буду смотреть») ведут себя read-your-writes: после успешной мутации изменение видно в любом разделе при следующем заходе без перезагрузки, а там, где мутация сделана — сразу.
- Сохранить источник истины на сервере: первая загрузка экрана по-прежнему из RSC-пропсов (правило `GUIDE.md`: данные в пропсах, клиентский остров не грузит данные при монтировании).
- Не откатывать ускорение навигации (`staleTimes`, prefetch).
- Провал мутации не оставляет «призрак» записи.

**Non-Goals:**
- Объединять серверные запросы `listWatchedRecords` и `listCatalog` в один.
- Переводить мутации с route handlers на server actions и менять контракт API.
- Трогать `staleTimes`, prefetch и прочие настройки кэша переходов.
- Чинить расхождение данных, приходящих из разных запросов, если их содержимое совпадает.

## Decisions

### D1. Единый клиентский стор личных списков (read-your-writes)

Модульный внешний стор (снапшот + подписки, чтение через `useSyncExternalStore`) с одним сидом из RSC-пропсов на всё приложение; провайдер монтируется в `src/app/(app)/layout.tsx`. `useWatchedRecords`/`useWatchlist` сохраняют сигнатуру как шов, но читают и пишут в общий стор.

Почему: экран, куда пользователь переходит, видит оптимистичную запись независимо от клиентского Router Cache — расхождение исчезает по построению и сразу для всех разделов (Home, My Films, My Series, detail, watchlist-вкладки). Альтернативы: React-контекст с `useState` (тот же эффект, но перерисовывает шире и хуже тестируется вне дерева); оставить только серверную инвалидацию (клиентский отклик зависит от гонок refresh/навигации).

Стор живёт в пределах сессии; при смене актора (ключ провайдера по id актора) состояние сбрасывается.

### D2. Серверная инвалидация после мутации (спайк первым шагом)

В `POST`/`DELETE` `/api/records` и `/api/watchlist` после успешной записи помечать затронутые маршруты протухшими (`revalidatePath` для `/`, `/films`, `/series`, `/me`, `/u/[handle]`, карточек `film/[tmdbId]`/`series/[tmdbId]`).

Почему: сервер — источник истины; инвалидация не зависит от порядка клиентских кликов и закрывает окно 30 c. Первым шагом — спайк: проверить, что `revalidatePath` из route handler сбрасывает именно клиентский Router Cache в Next 16.3.8 (а не только Data Cache). При отрицательном результате спайк фиксирует это; механизм заменяется на рабочий из имеющихся средств без перевода мутаций в server actions (объём не расширяем), а гарантию свежести несёт D1. Альтернативы: только `router.refresh()` (текущее, гонки остаются); server actions + `revalidateTag`/`updateTag` (крупная смена модели мутаций — вне объёма); `cacheComponents` (вне объёма).

### D3. Сверка пропсов не затирает неподтверждённое локальное

Стор принимает серверные пропсы, но при сверке объединяет их с локальными изменениями по `mediaKey`: неподтверждённая (в полёте) запись побеждает, подтверждённая (сервер вернул её) снимает флаг, провалившаяся — удаляется (откат). «Подпись» сверки учитывает комментарий (в текущей версии — нет).

Почему: без этого серверный снапшот, пришедший с опозданием, снова покажет пустой список и баг вернётся.

### D4. Откат при ошибке и безопасный временный id

При неуспешном сохранении/удалении оптимистичное изменение откатывается (как в `watchlist-store`). Временный идентификатор новой записи — не `tmdbId`, а служебное значение (локальный маркер), чтобы удаление во время полёта POST не адресовало чужую запись.

### D5. Совместимость интерфейсов

Сигнатуры `useWatchedRecords(initial)` и `useWatchlist(initial)` сохраняются (шов из архивного решения `ui-shell-and-live-feed`); `MyFilmsView`/`MySeriesView`/`HomeView`/`FilmDetail` меняют только источник состояния. `record-store.ts`/`watchlist-store.ts` остаются точками входа.

## Risks / Trade-offs

- [`revalidatePath` из route handler может не сбрасывать клиентский Router Cache в Next 16.3.8] → спайк первым шагом; при неудаче гарантию свежести несёт общий стор (D1), ограничение фиксируется в задачах, объём не расширяется.
- [Стор устаревает между сессиями/аккаунтами] → сброс состояния при смене актора (ключ провайдера по id).
- [Стор затрёт свежие серверные данные] → merge по `mediaKey` (D3), pending-wins; тесты на сверку.
- [Два источника чтения (`listWatchedRecords` vs `listCatalog`) дадут расхождение] → оба читают одни строки `ratings`; объединение запросов — отдельный кандидат, вне объёма.
- [Больше состояния — больше тестов] → расширяем `store-refresh.test.tsx`, добавляем тесты кросс-раздельного состояния и отката, e2e «отметил на главной → «Мои фильмы» без F5».

## Migration Plan

Без миграций БД. Поставка обычным релизом. Откат — вернуть по-экранные хуки и убрать вызовы `revalidatePath`; поведение API не менялось.

## Спайк 1.1: `revalidatePath` из route handler → клиентский Router Cache (Next 16.3.8)

**Итог: не сбрасывает.** `revalidatePath`, вызванный из route handler, помечает путь протухшим на сервере (Data/Full Route Cache); реальная инвалидация происходит «при следующем заходе» на путь. Сигнал о перезаписи кэша клиенту (`store.pathWasRevalidated` в `next/dist/server/web/spec-extension/revalidate.js`) передаётся только через ответ Server Action — у route handler нет канала к браузеру. Клиент со свежей записью Router Cache (`staleTimes.dynamic: 30`) при переходе на `/films` отдаёт свой снапшот без запроса к серверу, поэтому серверная пометка до него не доходит. Свежесть read-your-writes несёт общий клиентский стор (D1); серверная инвалидация (D2) закрывает окно только для реальных серверных отрисовок.

Основания:
- Документация `revalidatePath` (Next.js): «Route Handlers: Marks the path for revalidation. The revalidation is done on the next visit to the specified path… The invalidation only happens when the path is next visited»; для Server Functions — «Updates the UI immediately (if viewing the affected path)».
- Исходники `next@16.3.8`: `revalidatePath` → `revalidate()` → `store.pendingRevalidatedTags` + `store.pathWasRevalidated = ActionDidRevalidateStaticAndDynamic`; значение читается только в потоке ответа action.
- Наблюдение на живом стенде (https://learn-watcher-platform.duckdns.org, сборка без `revalidatePath`): клиентский Router Cache реально отдаёт переходы мгновенно, фоновые перевалидации сегментов идут раз в ~30 с; после `router.refresh()` (текущий механизм) в мутационной вкладке уходит перезапрос RSC всех маршрутов, но при сбоях сервера (502 / `ERR_CONNECTION_CLOSED`) переход отдаёт error-страницу; неуспешный `DELETE /api/records` (502) оставил оптимистично скрытую запись-«призрак» до F5 (живое подтверждение задачи 3.3).
