## Context

См. `proposal.md` - Why. Что есть сейчас:

- `src/modules/activity/types.ts` объявляет `ActivityKind`, включая `comment_created`; `repository.ts` кодирует виды числами (`comment_created` = 5) и маппит их обратно. Оба ленточных запроса (`listFeedEvents`, `listGroupFeedEvents`) выбирают все виды без фильтра, а `listGroupFeedEvents` уже ограничен группой.
- `src/modules/discussions/service.ts:103` пишет `comment_created` внутри транзакции `addComment`; `create` пишет `post_created` (строка 48).
- Два потребителя ленты: главная (`HomeView` → `SocialFeed`, данные из `/api/feed` и SSE `/api/feed/stream`) и вкладка группы (`GroupActivity`, SSR-чтение). `getVisibleEvent` питает живой стрим и не фильтрует виды.
- Модалки добавления: `MyFilmsView.AddRecordForm` и `MySeriesView.AddSeriesForm` показывают постоянный `<ul>` из `visible = committed ? matches : весь каталог`; `GroupRatings` — тот же пикер. Общий `SearchField`. Каталог — моки `data.ts` / `series-data.ts`; личные записи приходят из `listWatchedRecords` (сервер) и живут в `record-store` / `series-store`.
- БД: `activity_events.kind` — smallint, уникальных ограничений нет; код 5 закреплён за `comment_created`. Персональные оценки уже защищены от дублей ограничением `ratings_personal_key`.

## Goals / Non-Goals

**Goals:**

- Комментарий не создаёт событие активности и не появляется ни в одной ленте, включая уже записанные события.
- Обсуждение даёт ровно одно событие — его создание.
- Модалки добавления показывают только результаты после «Найти» и не предлагают то, что уже добавлено (Мои фильмы / Мои сериалы).

**Non-Goals:**

- Не менять схему `activity_events` и не удалять код `kind = 5`: старые строки должны читаться без ошибок.
- Не менять upsert групповых оценок: повторная оценка того же медиа в группе разрешена спецификацией `groups/ratings`.
- Не трогать `RatingForm`, `Modal`, `SearchField`, реальный каталог/TMDB и live-поиск внутри списков.
- Не добавлять миграции.

## Decisions

### 1. Не писать `comment_created` и не отдавать его из лент

Убрать `recordEvent({ kind: 'comment_created' })` из `addComment` — комментарий перестаёт порождать событие. Дополнительно исключить уже записанные события комментариев из чтения: в обоих запросах ленты добавить `e.kind <> <comment code>` и вернуть `null` из `getVisibleEvent` для события-комментария (иначе SSE продолжит пушить старые/живые события).

- Почему: требование «убрать везде» включает старые строки; фильтрация на чтении делает это без удаления данных.
- Альтернатива: писать событие и прятать только в UI — оставляет мусор и два места фильтрации; отклонено.

### 2. Сохранить `comment_created` в типах и маппинге

Оставить `comment_created` в `ActivityKind` и `KIND_NAME` (для декодирования старых строк), но убрать его из UI-подписей (`feed.ts`, `GroupActivity`) — эти ветки становятся недостижимы для ленты. Отдельную константу кода 5 вынести рядом с `KIND_CODE`, чтобы SQL-фильтр не хардкодил число.

- Почему: обратная совместимость чтения старых событий важнее чистоты типа; миграция не нужна.
- Альтернатива: удалить вид из типа и добавить миграцию — сложнее и ломает чтение истории; отклонено.

### 3. Результаты модалки — только после «Найти», с исключением уже добавленных

В `AddRecordForm` (Мои фильмы), `AddSeriesForm` (Мои сериалы) и пикере `GroupRatings` инициализировать `visible` пустым массивом, а не всем каталогом: `visible = committed ? matches : []`. Для «Мои фильмы» и «Мои сериалы» дополнительно исключить из `matches` медиа, уже присутствующее в `records` (по `movie.tmdbId` / `series.id`). Для группового пикера исключение не применяется — повторная оценка допустима.

- Почему: до «Найти» список не нужен и именно он давал ощущение «весь каталог»; исключение уже добавленных закрывает повторное добавление на уровне выбора.
- Альтернатива: оставить полный список и только дизейблить добавленные — противоречит «убрать список»; отклонено.

### 4. Форму оценки открывать по выбору результата

Выбор найденного элемента, как и сейчас, закрывает пикер и открывает `RecordModal` / `SeriesModal` с этим медиа. Дополнительной логики не требуется.

## Risks / Trade-offs

- [Фильтр по коду 5 в SQL] → вынести код рядом с маппингом и добавить тест, читающий ленту с событием-комментарием и проверяющий, что его нет.
- [SSE может запушить событие комментария, записанное до изменения] → `getVisibleEvent` возвращает `null` для вида `comment_created`.
- [Исключение уже добавленных по `tmdbId`/`series.id`] → идентификаторы каталога и записей совпадают (записи хранят тот же `mediaRef`), поэтому сопоставление корректно; при пустом результате показываем существующее состояние «Ничего не найдено».
- [Дубли могли попадать через `id` vs `mediaRef`] → сервер и так апсертит (`ratings_personal_key`), поэтому защита нужна только на уровне выбора в UI; после изменения дубль не собрать.

## Migration Plan

Изменение только кода, миграций нет. Порядок: сначала заархивировать базовые изменения (`ui-shell-and-live-feed`, `group-discussions-and-ratings`, `seeded-profiles-and-unified-search`), затем это изменение. Откат — revert коммита; данные не затрагиваются.
