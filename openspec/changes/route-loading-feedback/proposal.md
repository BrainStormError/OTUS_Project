## Why

Каждый переход между страницами приложения — это полный серверный рендер (все страницы помечены `dynamic = 'force-dynamic'`), а ни одной `loading.tsx` в проекте нет. Пока сервер считает страницу (3-5 секунд), на экране остаётся старая страница без индикатора загрузки, поэтому навигация ощущается как «зависание».

## What Changes

- **Маршрутный индикатор загрузки.** Добавляется route-level `loading.tsx`, который Next показывает сразу при переходе, пока данные ещё грузятся.
- **Оболочка остаётся на месте.** `loading.tsx` живёт внутри `(app)/layout.tsx`, поэтому сайдбар, топбар, футер и мобильный таббар не перерисовываются — скелетон занимает только область контента.
- **Один общий скелет.** Для всех авторизованных страниц используется один общий скелетон (заголовок + блоки/сетка), собранный из существующих `Skeleton`, `SkeletonText`, `SkeletonGrid`; отдельный скелетон — для маршрута входа.
- **Доступность.** Область загрузки помечается как `role="status"` с `aria-busy`, чтобы состояние озвучивалось вспомогательными технологиями.
- **Вне объёма:** скорость самого серверного рендера не меняется — не трогаем `force-dynamic`, CSP/nonce, кэширование TMDB и запросов к БД, клиентский router cache.

## Capabilities

### New Capabilities

- Нет. Изменение правит поведение существующей возможности (состояния интерфейса).

### Modified Capabilities

- `ui/interface-states`: требование «Loading state» расширяется на навигацию между маршрутами — при переходе оболочка экрана остаётся видимой, а в области контента показывается скелетон до прихода содержимого.

## Impact

- **Код:** новый общий компонент скелетона и `src/app/(app)/loading.tsx`, `src/app/(auth)/login/loading.tsx`; переиспользование `src/components/ui/skeleton.tsx`.
- **БД:** миграции не требуются.
- **Тесты:** unit на компонент скелетона; проверка, что при навигации оболочка сохраняется и показывается скелетон.
- **Вне объёма:** ускорение серверного рендера (кэш TMDB, запросы к БД), отказ от `force-dynamic`, клиентский кэш переходов.
