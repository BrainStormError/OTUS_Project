## Context

Группа сегодня: `groups` + `group_members` (роль `admin|member`), страница `/groups/[id]` показывает участников и заглушку статистики (`toGroup` кладет `EMPTY_STATS`). Активность уже умеет `group_id` и видимость «только участникам группы» (`VIEWER_VISIBILITY`), но события с `group_id` не пишет никто, кроме `group_joined`; enum `post_created`/`comment_created` зарезервирован миграцией 1710000000006, но ничего его не заполняет. Личные оценки (`watched_records`) живут в localStorage + `POST /api/records` и имеют уникальность `(user_id, media_kind, media_ref)` без измерения группы. Каталог медиа — моки (`data.ts`, `series-data.ts`), UX оценки — `RatingForm` (0–10, шаг 0.1, комментарий, дата) в модалке.

## Goals / Non-Goals

**Goals:**

- Форум группы: темы (только админ), комментарии (все участники), вкладка «Обсуждения».
- Групповые оценки: у каждого участника своя оценка медиа в группе, групповая оценка = среднее, вкладка «Оценки».
- Прикрепление ровно одного обсуждения к оцениваемому медиа (только админ).
- Вкладка «Активность» с событиями группы и кнопкой «К обсуждению».
- Страница группы целиком в табах: Обсуждения | Оценки | Активность | Участники | Статистика.

**Non-Goals:**

- Реальная статистика группы (остается как есть — отдельная работа).
- Реальный каталог TMDB, модерация/удаление тем и комментариев, реакции, вложения.
- Личная лента (`/feed`) — не меняем; групповые события в неё не включаем.

## Decisions

- **Отдельные таблицы, а не расширение `watched_records`.** `group_ratings` (id, group_id, user_id, media_kind, media_ref, title, year, genres, rating, comment, watched_at, created_at; UNIQUE (group_id, user_id, media_kind, media_ref); индекс (group_id, created_at DESC)). Личные оценки не затрагиваются, уникальность и вкладки не смешиваются. Альтернатива — колонка `group_id` в `watched_records` с частичными индексами: отклонена как размывание личного агрегата и усложнение обоих уникальных ограничений.
- **Ссылка на медиа живет у обсуждения, не у оценки.** `group_discussions` (id, group_id, author_id, title, media_kind NULL, media_ref NULL, created_at) + частичный уникальный индекс `ON (group_id, media_kind, media_ref) WHERE media_ref IS NOT NULL` — «одна групповая оценка = одно обсуждение» гарантирует БД. Обычные темы без медиа остаются валидными (форум). Альтернатива — `discussion_id` в `group_ratings`: отклонена — ломается при удалении оценки и не позволяет обсуждению существовать до/без конкретной оценки.
- **Модуль `discussions`, оценки — в `groups`.** Новый bounded context `modules/discussions` (темы + комментарии + прикрепление); групповые оценки и лента группы — сценарии `modules/groups`. Альтернатива — всё в `groups`: отклонена, модуль распухает и смешивает агрегаты; правило «modules/X не импортирует modules/Y/repository» соблюдаем через `modules/discussions/index.ts`.
- **Среднее — на чтении.** `AVG(rating)::numeric(3,1)` в GROUP BY по медиа; по правилам проекта агрегаты не хранятся «на веру». Раскрытая строка показывает индивидуальные оценки участников.
- **Лента группы — новый запрос в `modules/activity`.** `listGroupFeed(actor, groupId, {limit, cursor})`: проверка участника в сервисе, `group_id = $2` поверх существующей `VIEWER_VISIBILITY`, тот же keyset-курсор. Активность страницы группы — RSC-чтение; живое обновление через существующий SSE-канал не расширяем (Non-Goal).
- **Кнопка «К обсуждению» — джойн на чтении.** Лента группы для событий `film_rated`/`series_rated` добирает attached-обсуждение по `(group_id, target_type, target_id)`; href в payload не пишем — кнопка появляется и у старых событий после прикрепления. События групповых оценок пишутся с `kind = film_rated|series_rated` и `group_id` — отдельные kind не нужны.
- **Мутации.** `POST /api/groups/[id]/discussions`, `POST /api/discussions/[id]/posts`, `POST /api/groups/[id]/ratings`, `POST /api/groups/[id]/ratings/[media]/discussion` (attach). Все через `withRoute` + zod + rate limit; политики: `group:discuss` (member+), `group:discuss:create|attach` (admin) в `core/auth/policy.ts` c таблицей истинности.
- **UI.** Табы — URL-based (`/groups/[id]?tab=…` или подпути `discussions|ratings|activity`), RSC читает данные, интерактив — острова. Переиспользуем `RatingForm` (уже чистый компонент с валидацией), выбор медиа — тот же каталог-пикер из моков. Пустые состояния — через `EmptyState`, соответствуя `ui/interface-states`.

## Risks / Trade-offs

- [Attach «к оценке» при удалении всех оценок медиа] → серверная проверка «медиа должно быть оценено ≥1 участником» при attach; при удалении участником своей последней оценки существующее прикрепление не отзываем (обсуждение живет) — поведение фиксируется сценарием спецификации.
- [Среднее и «К обсуждению» — лишние запросы на чтение] → джойны в одном запросе ленты/списка оценок; индексы под каждый list-запрос (обязательное правило репозиториев).
- [Моковый каталог не сходится с `media_ref` реальных сущностей] → `media_ref` остается строкой (tmdbId), как в личных оценках; при появлении реального каталога миграция не нужна.
- [Табы без JS] → URL-based табы работают как ссылки, `?tab`/подпуть выбирается при реализации; на сценарии не влияет.

## Migration Plan

Три новые идемпотентные миграции (`group_discussions`, `discussion_posts`, `group_ratings`) после 1710000000008, каждая с `down`. Порядок деплоя: миграции → код. Откат: `down`-миграции + revert; существующие данные (пользователи, группы, личные оценки) не затрагиваются.

## Open Questions

- Табы: query-параметр vs подпути — решается при реализации, поведение из спецификаций не меняет.
- Нужна ли отмена участником своей групповой оценки (delete) — спецификация требует upsert; удаление оставлено за пределами первого среза и может быть добавлено без изменения схем.
