## Context

Мотивация и замеры — в `proposal.md`. Здесь только то, что определяет способ.

Исходное состояние:

- `src/app/layout.tsx:11` держит `export const dynamic = 'force-dynamic'`. Причина — per-request CSP-нонс: статический пререндер не может нести разный нонс в каждом ответе. Следствие — из `prerender-manifest.json` пререндерены только `/icon.svg` и `/_global-error`, всё остальное рендерится на каждый запрос.
- CSP собирается в `src/proxy.ts` (`createNonce()` + `buildCsp()`), мидлварь бежит на каждом запросе, кроме статики.
- Авторизация страницы — в `src/app/(app)/layout.tsx:17`: `getActor()` и `redirect('/login')`.
- API покрывает `records`, `watchlist`, `search`, `catalog/detail`, `genres`, `feed` и `friendships/search`. Для статического шелла не хватает GET-чтений: `me/identity` (был только PATCH), `me/privacy` (только PATCH), `me/profile`, `me/stats`, `profiles/[handle]`, списки `friendships`, `groups` (мои, поиск, приглашения) и `groups/[id]` (группа с ролью, обсуждения, оценки, активность, приглашения).
- Целевой хост — 1 ядро, 960 МБ. Рендер React на сервере соревнуется с базой за процессор.

## Goals / Non-Goals

**Goals:**

- Убрать рендер React с критического пути запроса и вернуть кэширование HTML.
- Снять `force-dynamic`, не ослабив политику безопасности скриптов.
- Перевести страницы на клиентские данные по одной за раз, не ломая приложение на каждом шаге.
- Сохранить сервер как единственную инстанцию решений о доступе к данным.

**Non-Goals:**

- Полный переход на SPA с отдельным роутером (вариант C). Отделено осознанно: он не даёт выигрыша, пока `/api/*` остаётся на Next.js, а перенос 30 обработчиков — отдельная работа.
- Пересмотр бюджетов `platform/resource-budgets` — это change `runtime-cost-trims-followup`.
- Оптимизация SQL, индексы, распараллеливание ходок — вторая очередь.
- Интеграция внешнего кэша или CDN.
- Ручная отрисовка скелетонов под каждую страницу — отменена решением о снятии состояния загрузки.

## Decisions

### 1. Вариант B (статический шелл в Next.js), а не вариант C (SPA)

**Решение:** остаёмся в Next.js, страницы собираются на сборке, данные тянутся клиентом через существующие `/api/*`.

**Почему не C:** 30 API-обработчиков уже написаны и покрыты тестами. Если их оставить на Next.js, выигрыш от C сводится к замене роутера и сборщика — мало за большую работу. Если переносить и API — это уже другой проект. B снимает ту же боль (`force-dynamic`, рендер в запросе) и остаётся ступенькой в C, если он понадобится.

**Альтернатива:** SSR только оболочки (вариант A). Отклонена как конечная цель, но остаётся промежуточным шагом миграции: на первом этапе оболочка ещё может рендериться на сервере, пока данные уезжают в клиент.

### 2. Hash-based CSP вместо per-request нонса

Сейчас inline-скрипты (тема, flight-payload Next.js) авторизуются нонсом, который `proxy.ts` генерирует на каждый запрос. Это и держит `force-dynamic`.

**Решение:** HTML становится байт-в-байт одинаковым (страницы собираются на сборке, данных пользователя в нём нет), значит содержимое каждого inline-скрипта стабильно и авторизуется его SHA-256 digest'ом. Политика фиксируется на сборке.

**Альтернатива:** оставить нонс. Отклонена — она и есть причина `force-dynamic`.

**Альтернатива:** убрать inline-скрипты полностью. Рассмотрена; часть inline-кода (flight-payload Next.js) не поддаётся выносу в отдельный файл без хирургии в рантайме Next.js. Hash решает задачу без этой хирургии.

**Ограничение, о котором надо помнить:** digest фиксируется на сборке. Любое изменение inline-скрипта требует новой сборки. Это уже так и есть с любым изменением кода, поэтому отдельной платы нет.

### 3. Guard авторизации: клиентский редирект плюс проверка куки в мидлвари

Серверный `redirect('/login')` в layout работал, потому что layout рендерился на сервере с сессией. Статический HTML сессии не знает.

**Решение из двух частей:**

- `proxy.ts` проверяет **наличие** session-куки и без неё отдаёт редирект. Это не проверка сессии, а проверка факта присутствия куки: без базы, без крипты, одна ветка. Убирает мелькание оболочки для обычного случая.
- Клиентский guard после монтирования сверяется с `/api/me/identity` и при отказе уводит на `/login`. Человек с протухшей кукой пройдёт мидлварь, но упрётся в 401 на данных.

Настоящая проверка сессии остаётся там, где была — в каждом `/api/*` через `withRoute` → `resolveActor` → чтение роли из БД.

**Альтернатива:** только клиентский guard. Отклонена — даёт заметное мелькание оболочки на каждом визите без сессии.

**Альтернатива:** полноценная проверка сессии в мидлвари. Отклонена — мидлварь бежит на каждый запрос, включая статику; проверка JWT там вернёт крипто-стоимость на путь каждого файла.

### 4. Оболочка перестаёт нести identity

`TopBar` получает `name`/`tag`, `ListStoreProvider` — `key={actor.id}` и `actorId`. В статическом HTML этих значений нет.

**Решение:** оболочка рендерится без identity; имя, ник и ключ сторов появляются после ответа `/api/me/identity`. До этого момента оболочка показывает нейтральное состояние аккаунта.

Это не «перенос авторизации в клиент»: клиент узнаёт, **кто** пользователь, чтобы нарисовать его имя. Решение, **что** он может, остаётся на сервере.

### 5. Миграция страниц — по одной за раз

17 страниц. Переводить все разом — сломать всё разом.

**Решение:** каждая страница переводится отдельным шагом. Схема шага одинаковая: убрать серверные обращения к модулям из `page.tsx`, перенести их в клиентский хук поверх `/api/*`, оставить JSX. Оболочка и роутинг не меняются, URL сохраняются, e2e-сценарии остаются валидными.

Порядок — от страниц с наименьшей связностью к наибольшей: `settings`, `me`, `friends` → `films`, `series` → `groups` → главная.

### 6. Скелетоны убираются

**Решение:** `loading.tsx`, `RouteLoadingSkeleton` и `ui/skeleton` (если больше нигде не используется) удаляются. Состояние загрузки отдельно не рисуется; область контента остаётся пустой, пока данные не придут.

**Что это стоит — записано явно, чтобы решение было осознанным:**

- Отменяется требование `ui/interface-states` о скелетонах (delta-спецификация в этом change'е это фиксирует).
- Теряется объявление «загрузка» для скринридеров, которое было в `Route navigation loading state` через `aria-busy`. Требование `ui/accessibility` об озвучке асинхронных изменений формально не нарушается (там речь о результатах и ошибках), но индикатор загрузки исчезает.
- На медленном соединении пользователь видит пустой прямоугольник вместо каркаса контента.

**Реверс дешёвый:** вернуть `aria-busy` на зарезервированную область — один атрибут, без отрисовки скелетонов. Если по факту станет мешать, это делается одной строкой и не требует нового change'а. Полноценные скелетоны не возвращаются: это и есть отменённый велосипед.

### 7. Эндпоинты чтения для экранов

Статистика, профиль и списки друзей/групп существуют только как серверные модули. Статический HTML их отдать не может.

**Решение:** добавить GET-чтения через существующий `withRoute`, чтобы они унаследовали проверку origin, валидацию схемы, rate limit и типизированные ошибки:

- `/api/me/identity` — кто пользователь (для нейтральной оболочки);
- `/api/me/privacy`, `/api/me/profile`, `/api/me/stats`;
- `/api/profiles/[handle]`;
- `/api/friendships` — друзья, входящие и исходящие заявки одним чтением;
- `/api/groups` — мои группы, доступные для вступления, приглашения;
- `/api/groups/[id]` — группа, роль, обсуждения, оценки, активность; приглашения только администратору.

Контракт чтения закрепляется delta-спецификацией `platform/http-contract`. Для чтений без сессии ответ — 401; для мутаций по-прежнему сначала отклоняется недоверенный origin.

### 8. Параметризованные URL отдаются статическим шеллом через rewrite

У `/film/[tmdbId]`, `/series/[tmdbId]`, `/films/[id]`, `/groups/[id]`, `/groups/[id]/admin` и `/u/[handle]` flight-payload содержит значение параметра. Значит, байты документа различаются для каждого URL (проверено: у `/groups/4` и `/groups/5` один inline-скрипт имеет разные digest'ы), а digest'ы всех возможных значений на сборке неизвестны.

**Решение:** эти URL объявляются rewrite'ами на статические страницы `/shell/*`. Документ одинаков для всех значений параметра; id читается клиентом из `usePathname()` после гидратации (`useSyncExternalStore`), поэтому серверный и первый клиентский рендер совпадают. Публичные URL не меняются.

**Альтернатива:** нонс только для параметризованных страниц. Отклонена — нарушает требование «ни одна страница не несёт per-request секрет».

## Risks / Trade-offs

- [HTML становится публичным] → Данных в нём нет. Защита данных остаётся на сервере и закреплена delta-спецификацией `platform/authorization`. Проверка: в отданном документе отсутствуют имя, ник, роль и идентификаторы пользователя.
- [Мелькание оболочки до редиректа] → Смягчено проверкой куки в `proxy.ts`. Полностью убрать нельзя: клиентский guard по определению работает после отрисовки.
- [Digest CSP фиксируется на сборке] → Любое изменение inline-скрипта требует новой сборки. Это совпадает с обычным циклом релиза. Риск забыть обновить digest при правке inline-кода → покрыть проверкой в CI: собрать, вытащить политику из ответа, сверить digest'и с фактическими inline-скриптами документа.
- [Снимается объявление загрузки для скринридеров] → Сознательная цена, см. Решение 6. Реверс — один атрибут `aria-busy`.
- [e2e-тесты завязаны на серверный рендер] → 11 файлов. URL и DOM сохраняются, тесты переживают миграцию. Сценарии, где поиск идёт в живой TMDB, зависят от доступности внешнего API: без него `/api/search` отвечает 500 и сценарий падает, это не регрессия шелла.
- [Двойной источник данных на время миграции] → Пока часть страниц на сервере, а часть на клиенте, одни и те же данные читаются двумя путями. Это временное состояние; тесты должны покрывать оба, пока миграция не завершена.
- [Префетч теряет смысл в текущем виде] → `nav-links.tsx` греет роуты через `router.prefetch`, а `prefetch={false}` на `Link`. Со статическим HTML ценность prefetch'а растёт (можно греть и документ, и данные). Пересмотр этой механики — отдельная задача, не блокирующая change.

## Migration Plan

1. Сначала выполнить change `runtime-cost-trims-followup`: освободить ядро, иначе эффект от статики смешается с эффектом от фоновой работы.
2. CSP: перевести `buildCsp` на hash-based, убрать `createNonce`, снять `force-dynamic` из корневого layout. Проверить, что страницы попадают в `prerender-manifest.json`.
3. Guard: проверка куки в `proxy.ts`, клиентский guard в оболочке, перенос identity на клиент.
4. Добавить чтения из Решения 7 и их тесты; параметризованные URL перевести на rewrite'ы из Решения 8.
5. Переводить страницы по одной в порядке из Решения 5, с прогоном e2e на каждом шаге.
6. Удалить скелетоны на последнем шаге, когда все страницы переведены и `loading.tsx` больше ничего не обслуживает.
7. Откат: постранично — вернуть серверное чтение конкретной страницы. Полный откат — предыдущий образ; схема БД этим change'ом не меняется.

## Open Questions

- Стоит ли после завершения пересмотреть механику prefetch в `nav-links.tsx` — со статическим HTML греть документ и данные становится дёшево и заметно полезнее. Не влияет ни на спецификации, ни на состав работ этого change'а.
- Нужен ли отдельный прогон тестов на доступность после снятия `aria-busy`, или достаточно ручной проверки скринридером на одной странице. Не влияет на контракт.
