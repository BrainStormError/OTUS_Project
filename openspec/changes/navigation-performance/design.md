## Context

Мотивация — в `proposal.md`. Текущее состояние, определяющее подход:

- Все страницы `(app)` объявлены `force-dynamic` (например `src/app/(app)/layout.tsx:10`, `src/app/(app)/page.tsx:16`), а CSP с per-request nonce ставится в `src/proxy.ts` — статического рендера нет by design.
- `next.config.js` не задаёт ни `experimental.staleTimes`, ни настроек prefetch. По умолчанию клиентский Router Cache для динамических маршрутов имеет `staleTime = 0`, поэтому каждый переход (в т.ч. «назад/вперёд») заново запрашивает RSC-снапшот с сервера.
- Ссылки оболочки и карточек — обычные `<Link>` без `prefetch` (`src/components/features/movie-tracker/MovieCard.tsx:43`, ссылки в `src/components/layout/*`).
- `SocialFeed` (`src/components/features/movie-tracker/SocialFeed.tsx:56`) открывает `EventSource('/api/feed/stream')` при монтировании и живёт только на главной (`src/components/features/movie-tracker/HomeView.tsx:186`). Любой заход на главную — новое подключение; серверный лимит — `CONNECT_LIMIT = 10` за `CONNECT_WINDOW_MS = 60_000` на пользователя (`src/app/api/feed/stream/route.ts:12`) плюс слот-гвард `MAX_STREAM_CONNECTIONS_PER_IDENTITY = 4` (`src/core/http/stream-guard.ts:6`). Ретрай — фиксированные 3 с (`RETRY_MS = 3_000`, `SocialFeed.tsx:22`) и полный `GET /api/feed` на каждую ошибку (`SocialFeed.tsx:72-78`).
- `HomeView` грузит жанры клиентским `fetch('/api/genres')` при монтировании (`HomeView.tsx:73-86`) — это нарушает правило проекта «клиентские острова не грузят данные при монтировании» (`GUIDE.md:21`).
- Постеры — сырой `<img src={poster}>` без `loading`, `decoding` и размеров (`MovieCard.tsx:49-53`); контейнер карточки уже держит `aspect-[2/3]`.
- Ограничение хостинга: контейнер приложения ~1 ГБ RAM, один Node-процесс, Postgres в той же сети compose.

## Goals / Non-Goals

**Goals:**
- Повторный заход в раздел и переход «назад/вперёд» не запускают новый полный серверный рендер.
- Клик по ссылке меню начинается с уже готовящегося целевого экрана.
- Лента сохраняет одно соединение между переходами и не упирается в лимит подключений при частых заходах.
- Главная перестаёт делать отдельный клиентский запрос жанров при появлении.
- Постеры не грузятся до необходимости и не вызывают сдвига разметки.

**Non-Goals:**
- Отказ от `force-dynamic`, изменение CSP/nonce, статический рендер.
- Проксирование изображений через свой origin или переход на `next/image` с кастомным лоадером.
- Изменения в БД, в кэше TMDB, в конфигурации Postgres/VPS, в размере heap Node.

## Decisions

### D1. Переиспользование клиентского кэша переходов

Включаем `experimental.staleTimes.dynamic` в `next.config.js`, оставляя `static` не меньше дефолта. Обоснование: страницы динамические, поэтому именно `dynamic`-окно определяет, будет ли браузер переиспользовать уже полученный RSC-снапшот вместо нового запроса. Кэш живёт **в браузере**, а не в процессе приложения, поэтому на лимит 1 ГБ не влияет.

Альтернативы: `cacheComponents` (крупная смена модели рендера — вне объёма); клиентская догрузка данных после навигации (противоречит server-first из `GUIDE.md` и не даёт мгновенной навигации по кэшу); ничего не менять (текущее поведение = полный рендер на каждый клик).

Важно: кэш переходов должен оставаться «read-your-writes». После клиентской мутации (`record-store`, `watchlist-store`) вызывается `router.refresh()` — в Next 16 он инвалидирует сегментный кэш (RSC-данные) для всех маршрутов, поэтому при следующем заходе в раздел («Мои фильмы»/«Мои сериалы») таблица перезапрашивается и показывает новую запись. Альтернатива — server actions с `revalidateTag`/`updateTag`: дала бы автоинвалидацию, но требует перевода всех мутаций с route handlers на actions (вне объёма).

### D2. Предзагрузка ограничена ссылками оболочки

`prefetch` включаем только на ссылках навигации (sidebar rail, mobile tab bar), но не на карточках каталога. Обоснование: в сетках 8-24 карточки; их предзагрузка дала бы десятки лишних серверных рендеров и запросов к БД/TMDB ради экономии одного перехода, то есть рост нагрузки без пользы. На оболочке ссылок 4-6 — предзагрузка дёшева.

Альтернативы: `prefetch={true}` на всех `<Link>` (отклонено по нагрузке); `experimental.prefetchInlining`/`partialPrefetching` глобально (увеличивает payload и не решает область применения — можно добавить позже отдельно).

### D3. Одно соединение ленты на приложение

Поднимаем клиент ленты в источник на уровне `(app)`-layout, а `SocialFeed`/`FeedStream` получают события из него, вместо того чтобы каждая точка монтирования открывала свой `EventSource`. Обоснование: сегодня уход с главной закрывает соединение, а возврат открывает новое — отсюда 429 при частых переходах. Одно соединение живёт, пока пользователь в приложении.

Альтернативы: поднять только серверный лимит (лечит симптом, а не лишние переподключения); оставить как есть (отклонено — именно это вызывает 429).

### D4. Восстановление без шторма

Заменяем фиксированные 3 с на нарастающую задержку с джиттером и не делаем полный `GET /api/feed` на каждую ошибку; отказ по лимиту (429) трактуем как «подождать», а не «повторить немедленно». Догон пропущенного по-прежнему опирается на `Last-Event-ID` (`feed/stream/route.ts:81-88`).

Альтернативы: оставить фикс. 3 с (петля сама выбивает лимит); ждать только `onerror` браузера без своего таймера (не даёт управления джиттером).

### D5. Жанры отдаются с сервера

`page.tsx` читает жанры через сервис и передаёт их в клиентский `HomeView` пропсами; клиентский `fetch('/api/genres')` при монтировании удаляется. Обоснование: убирает round-trip на каждый заход и соответствует правилу «данные приходят с сервера в пропсах».

Альтернативы: оставить клиентский запрос (лишний круг до сервера); префетчить `/api/genres` (лишняя сущность, жанры и так в БД).

### D6. Постеры: нативные атрибуты

Добавляем `loading="lazy"`, `decoding="async"` и явные размеры (пропорция `2/3` уже в контейнере). Обоснование: самый дешёвый способ — без новой зависимости, без прокси и без изменений сервера.

Альтернативы: `next/image` (нужен лоадер/домены/оптимизация на слабом хосте — вне объёма); свой image-proxy (отдельная задача).

## Risks / Trade-offs

- [Кэш переходов покажет устаревшее персональное состояние после мутации] → короткое окно свежести (30 c) и явный `router.refresh()` после мутации в `record-store`/`watchlist-store`; проверка: после сохранения оценки раздел «Мои фильмы»/«Мои сериалы» показывает новую запись (`tests/unit/store-refresh.test.tsx`).
- [Предзагрузка увеличивает число серверных рендеров] → ограничена ссылками оболочки (D2), не карточками.
- [Одно долгое соединение на вкладку вместо коротких] → по памяти нейтрально/лучше (шторм реконнектов дороже); количество ограничено слот-гвардом; лимит подключений остаётся защитой.
- [`loading="lazy"` может отложить постеры, видимые при первом экране] → браузер грузит видимые изображения сразу; при необходимости первые карточки можно оставить без `lazy`.
- [Правки не касаются памяти сервера] → `staleTimes` и `prefetch` живут в браузере, персистентных серверных кэшей не добавляется; ограничение 1 ГБ не затрагивается.

## Migration Plan

- Изменения конфигурации (`next.config.js`) и клиентских компонентов; миграций и изменений схемы нет.
- Деплой: обычная пересборка образа и перезапуск контейнера; откат — возврат конфигурации и компонентов (данных не теряется).
- Наблюдение после деплоя: повторный заход в раздел не делает нового RSC-запроса; при частых заходах на главную больше нет 429; на главной отсутствует запрос `/api/genres`.

## Open Questions

- Точное значение окна свежести `staleTimes.dynamic` — определяем при реализации (ориентир — десятки секунд), не влияет на сценарии спецификаций.
