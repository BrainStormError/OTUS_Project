## Context

Мотивация — в `proposal.md`. Текущее состояние, которое определяет подход:

- Каталог читает TMDB «живьём»: `src/modules/catalog/client.ts` (raw `fetch` с таймаутом `TMDB_REQUEST_TIMEOUT_MS = 5000`) вызывается из `src/modules/catalog/service.ts`. Кэш там — in-memory `TtlCache` на 60 секунд (`catalog/cache.ts`), это неограниченно растущая `Map`, которая теряется при рестарте процесса.
- Страницы ждут TMDB синхронно во время SSR: `src/app/(app)/page.tsx` (`searchCatalog`), `film/[tmdbId]/page.tsx` и `series/[tmdbId]/page.tsx` (`resolveDetail`).
- Персистентность идёт только через общий пул и версионированные миграции (`platform/data-access`); доменные сущности используют числовые первичные ключи, UUID запрещены (`data-model`).
- Развёртывание: один Node-процесс в Docker (`output: standalone`), Postgres в той же сети compose.

## Goals / Non-Goals

**Goals:**
- Ответы TMDB сохраняются персистентно и переиспользуются между запросами и между перезапусками контейнера.
- Прогретый кэш гарантирует, что рендер страницы не блокируется на сетевом таймауте TMDB.
- При недоступности TMDB отдаётся последнее известное значение, а не ошибка.
- Оболочка экрана отдаётся раньше медленных секций.

**Non-Goals:**
- Координация нескольких инстансов приложения, внешний CDN, тюнинг VPS/Postgres.
- Предзаполнение кэша (заполняем лениво, по запросу).
- Кэширование словаря жанров (он уже в БД) и изображений TMDB.

## Decisions

### D1. Персистентный кэш в Postgres (`tmdb_cache`)

Храним ответы TMDB в отдельной инфраструктурной таблице. Обоснование: переживает пересоздание контейнера, оперативная память приложения почти не растёт (данные на диске БД), совпадает с текущим стеком pg + миграции, легко тестируется.

Схема (соблюдает правило числового PK из `data-model` — никакого text/UUID в первичном ключе):

```
tmdb_cache
  id          bigint generated always as identity primary key
  cache_key   text not null unique          -- kind + нормализованные параметры + язык
  payload     jsonb not null                -- сырой ответ TMDB
  expires_at  timestamptz not null
  created_at  timestamptz not null default now()
  updated_at  timestamptz not null default now()
  index on (expires_at)                     -- для чистки
```

Альтернативы: встроенный кэш Next (`unstable_cache`/`use cache`) — проще, но теряется при `docker compose recreate`; in-memory кэш — растёт в RAM и теряется при рестарте (текущий `TtlCache` уже неограничен). Отклонены по причине «ограниченная память + Docker».

### D2. Read-through: свежее → TMDB на промахе → последнее известное при сбое

- Чтение: строка по `cache_key`; если `expires_at > now()` — вернуть `payload` (hit, без сети).
- Промах/истёк: вызвать TMDB (существующий таймаут). Успех — `upsert` и вернуть. Сбой/таймаут — вернуть `payload` истёкшей строки, если она есть (stale-on-error); если строки нет — вернуть ошибку как сейчас.
- Гарантия: прогретый кэш никогда не блокируется на TMDB.

### D3. Ограниченный рост

- TTL — константа модуля (например 6 часов), без изменения `platform/runtime-config`.
- Чистка: при записи удалять истёкшие строки этого ключа; лёгкий периодический свип удаляет строки старше окна хранения по индексу `expires_at`.
- `payload` — `jsonb` с публичными метаданными TMDB (секретов там нет).

### D4. Границы стриминга

- **Главная:** оболочка и `SearchField` рисуются сразу; «Популярное» и «Лента» становятся async-серверными компонентами под `<Suspense fallback={<скелетон/>}>`.
- **Детали (`film/[tmdbId]`, `series/[tmdbId]`):** страница возвращает оболочку сразу, блок детали стримится под `<Suspense>`; `notFound()` переносится внутрь async-секции.
- **Списки (`films`, `series`):** оболочка сразу, per-user секции стримятся.
- Требование к реализации: страница НЕ должна `await` медленные данные до возврата JSX.
- Взаимодействие с `route-loading-feedback`: `loading.tsx` показывается, пока не пришла оболочка маршрута; секционные `<Suspense>` закрывают медленные части внутри неё.

### D5. Ключ кэша

Детерминированный `cache_key` из `kind`, нормализованных параметров (query/genre/year/page) и языка. В `data-model`-совместимой схеме ключ хранится текстовой колонкой, но первичный ключ — числовой.

## Risks / Trade-offs

- [Таблица растёт] → TTL + чистка на записи + свип по индексу `expires_at`.
- [Отдаём устаревшие данные дольше TTL при сбое TMDB] → это требуемое поведение (bounded + last-known); `updated_at` помогает при отладке.
- [Миграция должна быть обратимой] → один файл с `up` и `down`.
- [Стриминг меняет семантику ошибок детали] → 404 обрабатывается внутри async-секции; e2e/юнит на путь «не найдено».
- [Форма `jsonb` может меняться между версиями TMDB] → храним сырой ответ, маппинг делаем при чтении (мапперы уже есть).
- [Гонка на промахе] → `INSERT ... ON CONFLICT (cache_key) DO UPDATE` идемпотентен.

## Migration Plan

- Добавить миграцию `..._create_tmdb_cache.sql` (up: таблица + индекс; down: drop).
- Деплой: мигратор выполняется до приложения (этап `migrator` в `Dockerfile` уже есть). Откат: `npm run db:rollback`; потеря кэша безопасна (просто холодный старт).
