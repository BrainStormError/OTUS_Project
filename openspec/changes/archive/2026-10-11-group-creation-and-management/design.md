## Context

См. `proposal.md` — Why. Текущее состояние:

- `groups` (`..._groups_and_tags.sql`): `name varchar(1000)`, `description varchar(1000)`, `tag_ids smallint[]`, `restricted boolean`, без ограничений уникальности имени. `group_members(group_id, user_id, role 0/1)`.
- `tags`: `id smallint PRIMARY KEY` **без identity/sequence**, `name varchar(80)`, уникальность `tags_name_key` по `name` (регистрозависимо).
- Вступление: `joinGroup` (`src/modules/groups/service.ts`) отклоняет `restricted`; приглашений нет — закрытые группы недостижимы.
- Права: `can()` (`src/core/auth/policy.ts`) — экшенов `group:create/update/invite/manage` нет.
- Админ-панель `AdminMemberPanel.tsx` — клиентский мок: приглашение/роль/удаление не сохраняются.
- Поиск людей уже есть: `GET /api/friendships/search` (`social/user-search`).
- `listDiscoverableGroups` (`repository.ts`) уже фильтрует `restricted = false`.
- `GroupsView.tsx` — клиентский, есть `searchGroups` с регистронезависимым матчем тегов.

## Goals / Non-Goals

**Goals:**

- Создание группы любым аутентифицированным пользователем через модалку и переход на её страницу.
- Настройки группы (имя/описание/теги/видимость) и управление участниками — реально сохраняются.
- Приглашения как единственный вход в закрытую группу.

**Non-Goals:**

- Публичные инвайт-ссылки/коды (только адресные приглашения по пользователю).
- Выход из группы участником, передача владения, удаление группы.
- Реальная статистика группы (остаётся существующий placeholder).

## Decisions

### 1. Миграции данных

- `tags.id` — добавить генерацию (`ADD GENERATED BY DEFAULT AS IDENTITY`, старт выше текущего максимума, чтобы не пересечься с засеянными 1..8).
- `tags` — снять `tags_name_key`, создать уникальный индекс `lower(name)`.
- `groups` — `CREATE UNIQUE INDEX groups_name_key ON groups (lower(name))`.
- `group_invitations(id bigint identity PK, group_id, inviter_id, invitee_id, status smallint 0/1/2, created_at, updated_at, UNIQUE(group_id, invitee_id), CHECK(inviter_id <> invitee_id))` + индексы по invitee/status и group/status.

### 2. Теги — upsert в общий словарь

`resolveTagIds(tx, names)`: trim + дедуп без учёта регистра, для каждого значения `INSERT ... ON CONFLICT ((lower(name)))` (выражение совпадает с уникальным индексом) с получением id; группа хранит `tag_ids`. Пустой ввод допустим.

- Почему вариat A из обсуждения: сохраняет числовые ссылки и текущий `GROUP_SELECT`, переиспользует существующие теги.
- Альтернатива: `text[]` в группах — теряет нормализацию; отклонено.

### 3. Сервисы и права

- `createGroup(actor, input)`: `withTransaction` — insert группы, insert создателя как `admin`, `resolveTagIds`. Возвращает id.
- `updateGroup(actor, { groupId, name?, description?, tags?, restricted? })`: проверка `can(actor, 'group:update', { groupRole })`; транзакция update + теги.
- `changeGroupRole` / `removeGroupMember`: `can(actor, 'group:manage', { groupRole })`.
- Приглашения: `inviteToGroup` (`group:invite`, admin), `listMyInvitations` (invitee), `respondInvitation` (invitee, accept/decline), `cancelInvitation` (admin).
- Новые экшены в `can()`: `group:create` (любой аутентифицированный, как `wish:create`), `group:update`, `group:invite`, `group:manage` (все admin по `groupRole`).

### 4. Инварианты приглашений и участников

- Приглашение отклоняется, если приглашаемый уже участник.
- Повтор pending-приглашения не создаётся; после `declined` — переоткрывается в pending (`ON CONFLICT (group_id, invitee_id) DO UPDATE SET status=0, inviter_id=..., updated_at=now()`).
- `accept` внутри транзакции ставит status=accepted и вызывает `insertGroupMember(tx, groupId, actor.id, 'member')` → обходит запрет `joinGroup` для закрытых групп.
- `cancel` удаляет pending-строку.
- Нельзя удалить/понизить последнего администратора группы (проверка в сервисе) — иначе группа останется без управления.

### 5. API

- `POST /api/groups` — создание.
- `PATCH /api/groups/[id]` — настройки группы.
- `PATCH /api/groups/[id]/members/[userId]` (роль), `DELETE ...` (удаление).
- `POST /api/groups/[id]/invitations` — пригласить; `POST /api/groups/invitations/[id]` (accept/decline); `DELETE /api/groups/invitations/[id]` — отозвать.

### 6. UI

- `GroupsView`: кнопка «Создать группу» → `CreateGroupModal` (имя, описание, теги-чипы, радио открытая/закрытая); после успеха `router.push('/groups/'+id)`; ошибка дубликата имени — в модалке.
- Блок входящих приглашений (`GroupInvitations`) с «Принять»/«Отклонить».
- Админ-страница: `GroupSettingsForm` (имя/описание/теги/видимость) + рабочая `AdminMemberPanel` (поиск человека через существующий поиск → приглашение, смена роли, удаление; список pending с отзывом).
- Общий компонент `TagInput` (чипы) для создания и настроек.

## Risks / Trade-offs

- [Пересечение id тегов при добавлении identity] → старт последовательности выше максимума существующих.
- [`ON CONFLICT` по выражению `lower(name)`] → нужен индекс ровно по `lower(name)`, иначе конфликт не сработает; покрываем тестом.
- [Гонка уникальности имени группы] → `23505` маппится в `CONFLICT`.
- [Удаление последнего админа] → сервис запрещает.
- [Приватность при выборе приглашаемого] → используем существующий поиск людей (скрытые профили не находятся); это осознанное ограничение.
- [Два change правят `ui/screens`] → change 1 меняет требования «Profile screen»/«Settings screen», этот — «Groups and admin panel»; заголовки разные, конфликта при архивации нет.

## Migration Plan

- Одна миграция: identity + уникальные индексы + `group_invitations`.
- Сид не меняется: существующие группы/теги валидны (имена уникальны, теги уже уникальны).
- Откат: удаление `group_invitations`, индексов и identity.
