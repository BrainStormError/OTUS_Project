## Context

Мотивация — в `proposal.md`. Текущее состояние, определяющее подход:

- Страница группы `src/app/(app)/groups/[id]/page.tsx` объявлена `force-dynamic` и читает `searchParams` (`?tab=`, `?discussion=`) — каждый переход по вкладке это новый RSC-запрос и полный SSR.
- Вкладки группы (`src/components/features/movie-tracker/GroupTabs.tsx:34`) — обычные `<Link href={`/groups/${id}?tab=${tab.id}`}>`, то есть серверная навигация; при этом оболочка страницы (группа, участники, права) перерисовывается заново на каждый клик.
- Проверка доступа дублируется на каждом слое: `GroupPage` вызывает `canViewGroup`, затем `getGroup` вызывает `canViewGroup` снова и после этого сам `findGroupById`, а панельные сервисы (`listGroupRatings` в `src/modules/groups/service.ts`, `listDiscussions`) вызывают `canViewGroup` ещё раз. `findGroupById` (группа + теги + все участники через JOIN users) выполняется3–4 раза на один рендер, плюс2–3 раза `getGroupRole`.
- Панели уже устроены по нужному паттерну: серверные `DiscussionsPanel`/`RatingsPanel`/`ActivityPanel` (`src/components/features/movie-tracker/GroupTabPanels.tsx`) читают данные и передают их клиентским `GroupDiscussions`/`GroupRatings`/`GroupActivity` пропсами. Клиентские компоненты данных при монтировании не грузят (`GUIDE.md:21`).
- Тот же паттерн «клиентские вкладки + данные с сервера» уже применён в `MyFilmsView` (вкладки «Просмотренные / Буду смотреть» — `useState`, обе таблицы приходят пропсами).
- URL-адресуемость обязательна: из ленты активности на главной и из панелей группы ведут диплинки `?tab=discussions&discussion=N` (`GroupActivity.tsx:75`, `GroupDiscussions.tsx:108,187`, `GroupRatings.tsx:309`).
- Ограничение хостинга: 1 vCPU / 1 ГБ RAM (`vps-resource-budgets`), поэтому каждый лишний SSR и SQL заметен; именно переходы внутри группы дают наибольшую нагрузку.

## Goals / Non-Goals

**Goals:**
- Переключение вкладок группы и открытие дискуссии не создают серверных запросов вообще.
- Первый заход на страницу группы читает каждую сущность (группу, роль, участников) не более одного раза.
- URL остаётся источником правды для диплинков и перезагрузки; кнопка «Назад» покидает страницу группы, а не проходит по вкладкам.
- Поведение прав доступа и контента вкладок не меняется.

**Non-Goals:**
- Изменение главной навигации между разделами (остаётся серверной: prefetch + Router Cache).
- Ленивая догрузка панелей по API (C2) и новые GET-эндпоинты для чтения панелей.
- Оптимизация `router.refresh()` после мутаций (сохраняется как есть, дешевеет за счёт дедупликации).
- Изменения БД, HTTP-контракта, TMDB-кэша, бюджетов ресурсов.

## Decisions

### D1. Жадная загрузка панелей за один серверный проход (C1)

Страница группы читает данные всех панелей (список обсуждений с открытой дискуссией, оценки, активность для участников, участники и статистика — уже входят в `GroupSummary`) и передаёт их клиентскому контроллеру вкладок. Обоснование: максимальный выигрыш на переключении (0 запросов), данные консистентны между вкладками, паттерн уже принят в `MyFilmsView`, правило «клиентские острова не грузят данные» не нарушается. Альтернативы: C2 с догрузкой панели по API при первом открытии (отклонён — требует новых GET-эндпоинтов и загрузки данных клиентом, противоречит `GUIDE.md:21`); оставить серверную навигацию с дедупликацией запросов (отклонён — лечит стоимость рендера, но не убирает серверный круг на клик, что и есть главная жалоба).

### D2. Клиентский контроллер вкладок с синхронизацией URL через replaceState

Вкладки становятся клиентским компонентом с `useState` для активной вкладки и открытой дискуссии; начальное значение приходит с сервера из `searchParams`, дальше изменения пишутся в URL через `history.replaceState` без записи в историю браузера. Обоснование: диплинки и перезагрузка продолжают работать, а кнопка «Назад» покидает группу (ожидаемое поведение для внутренних вкладок, согласовано в спеке). Альтернативы: `pushState` + обработка `popstate` (отклонён — «Назад» проходил бы по вкладкам, что противоречит спеке, и требуется дополнительная обработка); Next-навигация `router.replace` (отклонён — это по-прежнему серверный запрос RSC).

### D3. Дедупликация загрузки группы через react.cache

`findGroupById` и `getGroupRole` (или единая функция загрузки контекста группы) мемоизируются на серверный запрос через `react.cache` — как уже сделано с `getActor` (`src/modules/auth/session.ts`). Все слои (`GroupPage`, `getGroup`, `canViewGroup`, панельные сервисы) продолжают вызывать их как раньше, но каждый запрос выполняется один раз. Обоснование: минимальная правка без изменения сигнатур сервисов и правил авторизации (каждый слой по-прежнему проверяет права). Альтернативы: проброс уже загруженной группы в сервисы через параметры (отклонён — раздувает сигнатуры и смешивает слои); убрать `canViewGroup` из панельных сервисов (отклонён — ослабляет защиту в глубину).

### D4. Дискуссия — состояние контроллера, контент из того же прохода

Открытая дискуссия (`?discussion=`) живёт в том же клиентском состоянии, что и вкладка: её комментарии загружаются в серверном проходе вместе со списком обсуждений, а ссылки «открыть дискуссию» из панелей оценок и активности переключают вкладку и дискуссию локально. Обоснование: диплинки из ленты — вторая по частоте точка входа в группу, и она не должна снова стоить полный SSR. Альтернатива: оставить открытие дискуссии серверной навигацией (отклонён — сохраняет дорогой круг ровно на том сценарии, который начинает рабочий процесс в группе).

## Risks / Trade-offs

- **Первый заход в группу читает больше данных, чем одна вкладка** (обсуждения + оценки + активность разом) → нагрузка на SQL при первом заходе чуть выше; принято осознанно: один проход всё равно дешевле текущих3–4 полных рендеров, а панели ограничены (ленты — по лимиту, списки — по размеру группы). Следить за размером групп при росте.
- **Данные вкладок «протухают» между переключениями** (нет повторного чтения с сервера) → мутации в панелях продолжают обновлять состояние через `router.refresh()`, поэтому после изменений данные свежие; расхождение возможно только при действиях других участников до ближайшего обновления — соответствует текущему поведению Router Cache.
- **Кнопка «Назад» больше не проходит по вкладкам** → зафиксировано в спеке как намеренное поведение; диплинки и перезагрузка остаются рабочими, потери функциональности нет.
- **`router.refresh()` после мутаций всё ещё делает полный SSR** → дешевеет за счёт D3 (12 SQL → ~4), полный отказ от refresh вне объёма; если останется заметным — выносить в отдельный change.

## Migration Plan

Поставка через существующий CI/CD без миграций и изменений конфигурации; откат — обычный `previous`-образ из `scripts/deploy.sh`. Поведение прав доступа не меняется, поэтому откат безопасен без действий с данными. Проверка на стенде: переходы внутри группы не создают запросов (вкладка Network), повторный заход на страницу группы выполняет однократное чтение группы (счётчик запросов в тестах), диплинк `?tab=discussions&discussion=N` с главной открывает нужную дискуссию.
