## Context

Поиск людей на `/friends` — клиентский, поверх моков (`data.ts`: `searchFriends` → `otherUsers`). Реальные данные — только список друзей и входящие заявки (`modules/friendships`). API создания заявок нет: есть только accept/decline (`POST /api/friendships/accept|decline`), поэтому заявки попадают в систему только через seed. Схема БД готова: `friendships` имеет CHECK `requester_id <> addressee_id` и уникальный индекс пары, у `users` есть `profile_hidden`.

## Goals / Non-Goals

**Goals:**

- Поиск людей по БД: имя/handle, свои друзья в приоритете, фолбэк на все непрошедшие `profile_hidden` профили, свой профиль исключен.
- Рабочая отправка заявки из выдачи; статус отношений в каждом результате.
- Исходящие заявки в разделе «Заявки» + отзыв заявки.

**Non-Goals:**

- Поиск по группам (уже работает на данных из БД через `getGroups`/`getDiscoverableGroups`).
- Удаление друзей, приватность поиска, пагинация выдачи (лимит + offset по мере надобности), полнотекстовый поиск.

## Decisions

- **Поиск — серверный сценарий в `modules/friendships`** (`searchUsers(actor, query)`), а не отдельный модуль: данные и правила принадлежат домену дружбы, новый модуль ничего бы не добавил. Один SQL: friend-совпадения UNION-приоритет поверх общего пула; условие `u.id <> actor.id AND u.profile_hidden = false`; результат аннотируется статусом (`friend | pending_in | pending_out | none`) подзапросом по `friendships`. Альтернатива — два запроса и склейка в сервисе: отклонено как лишний раунд-трип и риск рассинхрона приоритета.
- **Создание заявки — `createFriendRequest(actor, addresseeId)`** c повторным использованием инвариантов БД: вставка `ON CONFLICT DO NOTHING` по уникальному индексу пары + явные проверки сервиса (self, уже принятая дружба, существующий pending) для читаемых ошибок. Статус `declined` не блокирует повторную отправку — новая строка поверх старой (индекс пары допускает конфликт: потребуется частичный уникальный индекс по pending либо переиспользование строки со сбросом статуса; выбор — переиспользовать существующую строку пары и поднимать её в `pending`, чтобы не плодить историю дубликатов).
- **Отзыв заявки — `withdrawFriendRequest(actor, friendshipId)`**: `DELETE` строки со статусом `pending`, где `requester_id = actor.id`. Принятые/отклоненные заявки не трогаем.
- **API**: `GET /api/friendships/search?q=`, `POST /api/friendships` (создание заявки), `DELETE /api/friendships/[id]` (отзыв) — по образцу существующих accept/decline через `withRoute` (origin guard, zod, rate limit).
- **Клиент**: `FriendsView` перестает читать моковый фолбэк; поиск ходит в API с дебаунсом, результаты рендерит `FriendListItem` с действием по статусу. Мок-функции `searchFriends`/`otherUsers` остаются только для unit-тестов компонентов.
- **Политика**: новые действия в `core/auth/policy.ts` (`friend:request`, `friend:withdraw`), покрытые таблицей истинности в unit-тестах.

## Risks / Trade-offs

- [Re-request после declined при переиспользовании строки пары] → решение фиксируется в design и покрывается integration-тестом; история отказов не сохраняется — для курса это приемлемо.
- [Поиск без пагинации при большом числе пользователей] → жесткий `LIMIT` (например 20) в схеме; пагинация — отдельное изменение.
- [Гонка двух одновременных заявок друг другу] → уникальный индекс пары делает вторую вставку no-op; сервис возвращает статус `pending`, а не ошибку.

## Migration Plan

Миграций схемы не требуется (только при выборе частичного уникального индекса — тогда одна идемпотентная миграция). Откат — revert кода; данные не затрагиваются.

## Open Questions

- Частичный уникальный индекс по pending-паре vs переиспользование строки: финализируется при реализации (интеграционный тест определит выбор); на поведение из спецификаций не влияет.
