## Context

Мотивация и замеры — в `proposal.md` (см. раздел Why). Здесь только то, что нужно для выбора способа.

Ограничения, которые определяют подход:

- Целевой хост — 1 ядро (`nproc = 1`), 960 МБ RAM, `shared_buffers=64MB`. Любая фоновая работа в момент рендера напрямую попадает в TTFB.
- Бюджет кэша и параметры Postgres зафиксированы в `platform/resource-budgets` и **не меняются** этим change'ом. Пересмотр чисел — отдельное решение после замера.
- Порядок вытеснения и соблюдение бюджета уже законтракчены в `catalog` и `platform/resource-budgets`; их поведение обязано сохраниться.

## Goals / Non-Goals

**Goals:**

- Убрать обслуживание кэша из критического пути запроса.
- Сделать стоимость вытеснения независимой от размера кэша.
- Не тащить `payload` через pg-протокол ради проверки срока.
- Дать планировщику Postgres реальную статистику.

**Non-Goals:**

- Пересмотр числовых бюджетов (100 МБ кэш, 64 МБ `shared_buffers`, 4 МБ `work_mem`, 20 соединений).
- Оптимизация SQL-запросов страниц, индексы, распараллеливание ходок — это вторая очередь, после того как ядро освободится.
- Перевод страниц на клиентские данные — это change `static-shell`.
- Внешние кэши (Redis, CDN) — не нужны, хост один, память ограничена.

## Decisions

### 1. Sweep на таймере, а не из `readThrough`

`src/modules/catalog/service.ts` сейчас зовёт `sweepExpiredIfDue` из `readThrough` после успешной записи. Это fire-and-forget (`void ... .catch()`), но он занимает ядро и соединение пула в тот же момент, когда рендерится страница.

**Решение:** один фоновый таймер в процессе с интервалом, превышающим частоту обращений, и защитой от повторного запуска, пока предыдущий проход не завершился.

**Альтернатива:** cron/отдельный контейнер. Отклонена — хост один, лишний процесс ест то же ядро, а деплой удорожается. Таймер внутри процесса уже переживает рестарт, а деплой перезапускает процесс.

**Альтернатива:** оставить в `readThrough`, но раз в N минут. Отклонена — связка «обслуживание ↔ запрос» остаётся, и попадание таймера всё равно выпадает на какой-то запрос.

### 2. Вытеснение обходом по индексу с ранней остановкой

Сейчас `deleteOldestCache` (`src/modules/catalog/cache-repository.ts`) считает `SUM(payload_bytes) OVER (ORDER BY updated_at ASC, id ASC)` по всей таблице и фильтрует по порогу. Стоимость O(N) по числу строк, плюс сортировка при `work_mem=4MB` уходит на диск.

**Решение:** читать записи в порядке `updated_at ASC, id ASC` (этот порядок уже покрыт `tmdb_cache_updated_at_idx`), накапливать `payload_bytes` и останавливаться, как только набран нужный объём. Удалять только то, что реально просмотрено.

**Альтернатива:** хранить суммарный объём в отдельной таблице-счётчике. Отклонена — добавляет таблицу и транзакционность ради того, что решается выборкой с остановкой.

**Альтернатива:** ограничить вытеснение `LIMIT N`. Отклонена — N пришлось бы подбирать под средний размер payload'а, а он у TMDB разный (поиск против детали с кредитами).

### 3. Проверка TTL отдельным запросом от чтения `payload`

`selectCacheEntry` сейчас выбирает `payload, expires_at` одним запросом. Просроченная запись стоит столько же, сколько свежая.

**Решение:** сначала читать `expires_at`; `payload` — вторым запросом только для свежей. На промахе кэша это одна лишняя ходка, но промах и так уходит в TMDB за сотни миллисекунд; на попадании — минус трафик.

**Альтернатива:** `SELECT expires_at` всегда, затем `SELECT payload`. Принято. Альтернатива «читать всё одним запросом» — это текущее поведение, от него уходим.

### 4. `VACUUM ANALYZE` шагом деплоя

Статистики нет ни по одной таблице (`n_live_tup = 0`, `last_autovacuum` пуст почти везде). Отдельного сервиса нет, autovacuum на таком хосте срабатывает нестабильно.

**Решение:** `scripts/deploy.sh` добавляет шаг после миграций и до `compose up` — `VACUUM ANALYZE` через временный контейнер migrator'а, ровно как это уже сделано для `db:migrate` и `sync-genres`.

**Альтернатива:** миграция с `VACUUM ANALYZE` внутри. Отклонена — миграция выполняется один раз на схему, а статистику надо обновлять при каждом деплое, когда меняются данные.

## Risks / Trade-offs

- [Таймер живёт в процессе Node] → При рестарте контейнера таймер стартует заново. Ничего не теряется: уборка идемпотентна, а пропуск одного прохода безопасен.
- [Таймер может совпасть с пиком] → Защита от повторного запуска и тот факт, что вытеснение теперь ограничено объёмом работы, снижают длительность прохода. Если по замеру окажется всё ещё заметно — интервал можно увеличить без изменения контракта.
- [Две ходки вместо одной на проверку TTL] → На промахе это незаметно (промах и так уходит в TMDB). На попадании — выгода от того, что не тащим `payload`, перекрывает лишнюю ходку. Критерий проверки: размер ответа pg-протокола на попадании не должен включать `payload` до подтверждения свежести.
- [`VACUUM ANALYZE` в деплое занимает время] → На текущих объёмах — доли секунды. Шаг идёт до старта приложения, поэтому пользователь его не видит; при росте данных его стоит перенести в фон, но это выход за рамки change'а.
- [Мы не доказали, что sweep — главный пожиратель ядра] → Замер этого не показывал. Поэтому в tasks сначала идёт измерение до/после: если TTFB не сдвинется, причину искать дальше (см. Open Questions).

## Migration Plan

1. Замерить базовый уровень на стенде: TTFB страницы, `count(*)` в первой сессии psql, `docker stats` по app/db.
2. Внести правки кода (sweep на таймере, вытеснение с ранней остановкой, проверка TTL отдельно).
3. Добавить `VACUUM ANALYZE` в `scripts/deploy.sh`.
4. Прогнать `npm run lint`, `npm run typecheck`, `npm run deps:check`, `npm test`, `npm run test:integration`.
5. Повторить замеры из п.1 и сравнить.
6. Откат — обычный: деплой предыдущего образа. Схема БД не меняется, миграций нет, откат кода безопасен.

## Open Questions

- Если после этой правки TTFB остаётся выше ~300 мс — следующий кандидат на пересмотр это числа `platform/resource-budgets` (`tmdb_cache` 100 МБ при `shared_buffers=64MB`, само `shared_buffers`). Решение принимать по замеру, отдельным change'ом.
- Стоит ли позже перевести уборку в autovacuum-подобный фон за пределами Node (отдельный контейнер или `pg_cron`). На текущих объёмах преждевременно.
