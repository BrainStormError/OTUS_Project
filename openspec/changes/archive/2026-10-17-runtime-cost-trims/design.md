## Context

Мотивация — в `proposal.md`. Текущее состояние, определяющее подход:

- `src/components/layout/nav-links.tsx:55` ставит `prefetch` на все 6–7 пунктов меню: для динамических `force-dynamic` маршрутов каждый prefetch — полный SSR с `getActor` и запросами страницы, то есть одно открытие страницы обходится в 1 + ~7 рендеров. Требование «Shell links prefetch their destination» введено change'ом `navigation-performance` (13/13 задач, не заархивирован).
- `resolveActor` (`src/modules/auth/actor.ts:11`) делает `findUserById` на каждый серверный запрос; сессия — JWT (`src/modules/auth/auth.ts:39`), но требование `platform/authorization` запрещает доверять роли из токена. Уже есть прецедент мемоизации на запрос — `getActor` обёрнут в `react.cache` (`src/modules/auth/session.ts`).
- Словарь жанров читается из БД на каждый `searchCatalog` (`storedGenreMap`, `src/modules/catalog/service.ts:81`) и на каждый `GET /api/genres` (его дёргают модалки `AddRecordModal.tsx:43`, `GroupRatings.tsx:84`); жанры меняются только скриптом `db:sync-genres`, который выполняется в деплое (контейнер перезапускается).
- `selectCacheUsageBytes` (`src/modules/catalog/cache-repository.ts`) — `SUM(octet_length(payload::text))` по всей `tmdb_cache` (до 100 МБ JSON) на каждом sweep'е (раз в ≤5 мин); `deleteOldestCache` повторяет тот же детоаст в оконной функции. Требование бюджета кэша — из change'а `vps-resource-budgets` (задеплоен), его поведение сохраняется.
- Postgres в compose (`docker-compose.yml`, сервис `db`) уже настроен (`shared_buffers=64MB`, `work_mem=4MB`, `max_connections=20`); JIT включён по умолчанию.
- `revalidatePersonalData` (`src/app/api/personal-revalidate.ts`) вызывает `revalidatePath` на 9 маршрутов из `POST`/`DELETE` `/api/records` и `/api/watchlist`; спайк 1.1 change'а `records-store-and-revalidate` показал, что в Next 16.3.8 это НЕ сбрасывает клиентский Router Cache — свежесть между разделами несёт общий стор (`list-store.ts`). E2E-страж — `tests/e2e/records-freshness.spec.ts`.

## Goals / Non-Goals

**Goals:**
- Открытие страницы перестаёт оплачивать SSR всех пунктов меню; переходы остаются быстрыми за счёт намеренного и фонового прогрева.
- Убрать повторяющиеся SQL на каждый запрос (актор, жанры) и периодический детоаст всего кэша TMDB.
- Сохранить все поведенческие контракты: роль только из БД, свежесть личных списков без F5, бюджет кэша 100 МБ, жанры из локального каталога.
- Каждое решение обратимо независимо от остальных.

**Non-Goals:**
- Отказ от `force-dynamic`, переход на статику, изменение CSP/nonce.
- JWT-claims для роли (прямо запрещено `platform/authorization`), Redis/внешние кэши.
- Пересмотр бюджетов памяти (`vps-resource-budgets`) и настроек пула БД.
- Интервал healthcheck (п.6 из обсуждения в этот change не входит).
- Полный отказ от `router.refresh()` после мутаций.

## Decisions

### D1. Prefetch по намерению и в простое вместо автопрефетча

Убираем `prefetch` с `<Link>` в `nav-links.tsx` и добавляем программный `router.prefetch()`: на `pointerenter`/`focus` пункта (намерение) и последовательный прогрев оставшихся пунктов через `requestIdleCallback` (с таймерным fallback) после монтирования оболочки. Прогрев отменяется при размонтировании и не стартует повторно в пределах жизни оболочки. Обоснование: снимает ×7 SSR с каждой загрузки, оставляя «клик почти всегда по тёплому кэшу»; `staleTimes.dynamic: 30` из `navigation-performance` продолжает работать. Альтернативы: оставить автопрефетч на 2–3 «горячих» пунктах (отклонён — остаётся умножитель и непонятно, какие пункты горячие); полный отказ от префетча (отклонён — регрессия скорости переходов, противоречит цели `navigation-performance`); `prefetch={false}` + hover-only (отклонён — на touch hover нет, переходы заметно замедлятся).

### D2. Кэш актора в памяти процесса с TTL и явной инвалидацией

`resolveActor` читает пользователя через модульный кэш (`Map<userId, {actor, expiresAt}>`) с TTL 60 с; мутации профиля (`/api/me/identity`, иные, меняющие `users`) сбрасывают запись актора. Роль и существование пользователя всегда берутся из этого кэша-БД-чтения, никогда из токена — требование `platform/authorization` сохраняется в форме «БД или кэш, полученный из БД ≤60 с назад, с инвалидацией при мутации». Обоснование: минус один SQL на каждый запрос; сброс при мутации даёт мгновенную видимость правок профиля; TTL 60 с ограничивает окно старения роли. Альтернативы: JWT-claims для роли (отклонён — прямой запрет спеки, роль из токена не доверяется); `react.cache` (отклонён — действует только в рамках одного запроса, дублей внутри запроса он уже убирает); убрать чтение из БД полностью (отклонён — нарушение спеки).

### D3. Кэш словаря жанров в памяти процесса (TTL 10 мин)

`listGenres`/`storedGenreMap` читают БД через модульный кэш списка жанров с TTL 10 минут; деплой перезапускает контейнер — кэш стартует пустым, поэтому синхронизация жанров из `db:sync-genres` видна сразу после деплоя. Обоснование: одна обвязка для обоих потребителей (поиск и `/api/genres`), поведение совпадает с чтением из БД в пределах деплойного цикла. Альтернативы: кэш без TTL до рестарта (отклонён — ручной запуск `db:sync-genres` без рестарта не увидит новых жанров); инвалидация по триггеру БД (отклонён — лишний механизм ради редкого события).

### D4. Cache-Control на `/api/genres` — `private, max-age=3600`

Ответ помечается `Cache-Control: private, max-age=3600`. `private`, потому что endpoint требует сессии (`resolveActor: getActor`) — общий прокси не должен кэшировать чужие ответы; `max-age=3600` согласован с границей свежести в спеке. Обоснование: убирает повторные запросы из модалок. Альтернативы: `public` (отклонён — ответ за авторизацией); `no-store` (статус-кво); ETag/304 (отклонён — всё равно round-trip, выигрыш меньше).

### D5. `payload_bytes` в `tmdb_cache` вместо детоаста payload'ов

Новая миграция: колонка `payload_bytes integer NOT NULL` (или `bigint`), одноразовый backfill `UPDATE ... SET payload_bytes = octet_length(payload::text)`, запись значения при `upsertCacheEntry` (та же транзакция). `selectCacheUsageBytes` становится `SELECT SUM(payload_bytes)`, `deleteOldestCache` считает оконную сумму по `payload_bytes`. Поведение бюджета (100 МБ, вытеснение старых, hysteresis 90 МБ из `vps-resource-budgets`) не меняется — меняется только стоимость подсчёта. Обоснование: sweep перестаёт детоастить до 100 МБ JSON каждые ≤5 минут; счётчик точен (считается от того же `octet_length(payload::text)`), расхождение исключено, если все записи идут через `upsertCacheEntry`. Альтернативы: счётчик в отдельной таблице с атомарным `+/-` (отклонён — больше механизмов, та же точность); `pg_column_size` (отклонён — другая семантика размера, не совпадает с бюджетом); считать размер в приложении по `JSON.stringify` (отклонён — расхождение с `octet_length` из-за кодировки).

### D6. `jit=off` в command сервиса `db`

Флаг добавляется в существующий `command:` рядом с `shared_buffers`/`work_mem`/`max_connections` в `docker-compose.yml`. Обоснование: одна строка, убирает CPU-накладные на JIT-компиляцию мелких планов; на 1 vCPU это заметно. Альтернативы: `plan_cache_mode` (не требуется при выключенном JIT); тюнинг через `postgresql.conf` (отклонён — `vps-resource-budgets` уже выбрал `command:` как единственный источник конфигурации).

### D7. Удаление `revalidatePersonalData`

Удаляются `src/app/api/personal-revalidate.ts` и его вызовы в `/api/records` и `/api/watchlist`. Свежесть личных списков целиком остаётся на общем сторе (`list-store.ts`) и `router.refresh()` — это уже подтверждено спайком 1.1 и покрыто e2e `records-freshness`. Обоснование: минус 9 служебных операций на каждую мутацию без изменения наблюдаемого поведения. Альтернативы: сократить список маршрутов до реально затронутых (отклонён — спайк показал, что механизм в Next 16.3.8 не сбрасывает Router Cache, сокращение бессмысленно); оставить как есть (отклонён — чистые накладные).

## Risks / Trade-offs

- **Первый клик по «холодному» пункту меню без hover (touch)** → переход идёт обычной навигацией, а не по тёплому кэшу; на практике touch-тап подсвечивает пункт перед активацией, а idle-прогрев к тому моменту уже отработал. Митигация: idle-прогрев стартует сразу после монтирования оболочки.
- **Актор/роль стареют до 60 с** (уволенный администратор остаётся админом до минуты) → зафиксировано в спеке `platform/authorization`; мутации профиля инвалидируют кэш мгновенно. Окно можно ужесточить TTL без изменения архитектуры.
- **Жанры из кэша процесса и браузера стареют до часа** → граница зафиксирована в спеке `catalog/genres`; деплой (перезапуск процесса) сразу освежает серверный кэш, браузерный — в пределах часа.
- **`payload_bytes` расходится с реальностью**, если где-то пишут мимо `upsertCacheEntry` → все записи идут через одну функцию; плюс задача теста на совпадение `SUM(payload_bytes)` с `octet_length` после backfill.
- **Отказ от `revalidatePath` ослабляет будущие экраны вне общего стора** → e2e `records-freshness` — контракт; новый экран с личными данными обязан подключаться к стору (правило уже в `records-store-and-revalidate`).
- **Сборка change'ов-зависимостей**: `ui/navigation`-дельта модифицирует требование из не заархивированного `navigation-performance` → архивировать `navigation-performance` первым (зафиксировано в proposal и здесь).

## Migration Plan

Стандартный CI/CD без ручных шагов: миграция `payload_bytes` проходит через существующий шаг `migrate` до `up` (порядок в `scripts/deploy.sh` уже такой); `docker-compose.yml` и код доставляются тем же деплоем. Откат: `previous`-образ требует down-миграции (`db:rollback` удаляет колонку `payload_bytes`) — колонка `NOT NULL` без DEFAULT, старый код её не заполняет, поэтому запись TMDB-кэша на новых ключах без down-миграции падает; откат compose-флага `jit=off` — тем же rollback'ом. Порядок архивации: сначала `navigation-performance` (источник требования префетча), затем этот change. Проверка после деплоя: `SHOW jit` = `off`; Network-вкладка — отсутствие пачки prefetch-запросов при загрузке и прогрев в простое; `docker stats` при активной навигации ниже прежних ~30%/9%.
