## Context

См. `proposal.md` — Why. Текущее состояние: `src/core/db/migrations/` содержит 12 SQL-миграций; доступ к БД идёт через `repository.ts` каждого модуля (`src/modules/*`), сервис владеет транзакцией (`withTransaction`), схема меняется только миграцией (`docs/03-data.md`). Архитектурные ограничения: `core` не знает о `modules`; модуль может обращаться к другому модулю только через его public `index.ts`, не через чужой `repository` (`.dependency-cruiser.cjs`). `node-pg-migrate` — SQL-миграции, у каждой `up` есть `down`. Идентификаторы пользователя протекают в JWT-сессию (`token.uid`) и в keyset-курсоры ленты.

## Goals / Non-Goals

**Goals:**

- Компактная нормализованная схема: числовые id, id-связи, минимальные типы.
- Единая сущность медиа и единая модель оценок.
- Целостность ленты через FK, без denormalized `payload`.
- Ограничение пользовательского текста 1000 знаками.
- Согласованные тестовые данные.

**Non-Goals:**

- Реальный каталог TMDB и синхронизация медиа из внешнего источника (внешний справочник остаётся строкой-ключом).
- Изменение UX/навигации экранов (поведение `ui/*` сохраняется).
- Продакшн-совместимость существующих данных: проекта учебный, данные пересоздаются.

## Decisions

### Числовые id: bigint identity

PK/FK — `bigint GENERATED BY DEFAULT AS IDENTITY` (BY DEFAULT, чтобы seed мог задавать фиксированные id). Удаляются `pgcrypto` и `gen_random_uuid`.
Альтернатива — `integer`: на 4 байта меньше, но `bigint` даёт запас и единый тип; выбрано пользователем.
Следствие для кода: `pg` возвращает `int8` строкой — вводится один парсер (`pg.types.setTypeParser(20, Number)`) в `core/db`.

### Сущность media

```text
media(id, kind smallint, external_ref varchar(128), title varchar(1000),
      year smallint, genre_ids smallint[])
  UNIQUE(kind, external_ref)
```

Заменяет пару `media_kind`/`media_ref` и копии `title`/`year`/`genres`. `ratings.media_id` и `group_discussions.media_id` ссылаются на неё. `extra_ref` (TMDB id или slug) остаётся строкой — это внешний бизнес-ключ, не наш идентификатор.
Альтернатива — оставить метаданные в строках оценок: отклонена (дублирование, рассинрон).

### Единая ratings с nullable group_id

```text
ratings(id, user_id FK, media_id FK, group_id FK NULL,
        rating smallint, comment varchar(1000), watched_at date, created_at)
  UNIQUE(user_id, media_id) WHERE group_id IS NULL
  UNIQUE(group_id, user_id, media_id) WHERE group_id IS NOT NULL
  INDEX(user_id, created_at DESC, id DESC)
  INDEX(group_id, created_at DESC, id DESC) WHERE group_id IS NOT NULL
```

NULL `group_id` — личная оценка, задан — групповая. Заменяет `watched_records` и `group_ratings`.
`rating` — `smallint` в десятых долях (0..100); маппинг «0..10 с шагом 0.1» ↔ код делается на границе repository/типов.
**Границы модулей**: общая таблица нарушает «таблица принадлежит модулю». Вводится новый модуль `modules/ratings`, владеющий таблицей; `records` и `groups` вызывают его public-функции и не трогают чужой repository (соблюдение `no-cross-module-repository`).
Альтернатива — две таблицы с `media_id`: отклонена (дубль схемы и связей).

### Коды вместо текста, справочники жанров/тегов

```text
genres(id smallint PK, name varchar(80))
tags(id smallint PK, name varchar(80))
groups(..., tag_ids smallint[], ...)
media(..., genre_ids smallint[], ...)
```

Enum → `smallint`-коды: `users.role` (0 employee, 1 admin), `friendships.status` (0 pending, 1 accepted, 2 declined), `group_members.role` (0 member, 1 admin), `media.kind` (0 film, 1 series), `activity_events.kind` (0 film_rated, 1 series_rated, 2 friendship_accepted, 3 group_joined, 4 post_created, 5 comment_created).
Справочники жанров/тегов — маленькие таблицы кодов; id задаются явно (не identity), чтобы ссылки в массивах были стабильны и seed детерминирован. Допустимость кодов проверяется CHECK; ссылочная целостность элементов массива не гарантируется FK (осознанный компромисс ради минимума связей).
Альтернатива — M:N с таблицами-связками: отклонена по требованию «минимум связей».

### activity_events без payload

```text
activity_events(id, actor_id FK, kind smallint, group_id FK NULL,
                media_id FK NULL, discussion_id FK NULL, created_at)
  INDEX(created_at DESC, id DESC)
  INDEX(actor_id, created_at DESC)
  INDEX(group_id, created_at DESC)
```

`payload` и `target_type`/`target_id` удаляются. Лента (`toFeedEvent`) берёт `title`/`rating`/`href` из `media` и `ratings`; `post_created`/`comment_created` — из `discussion_id`. Триггер `pg_notify` сохраняется.
Альтернатива — оставить полиморфный `target_id int`: отклонена (нет целостности, условные джойны).

### Прочие таблицы

`users` (id, email varchar(254) UNIQUE, name varchar(1000), handle varchar(50) UNIQUE, role smallint, provider varchar(32), provider_subject varchar(255), profile_hidden, stats_hidden, created_at, updated_at); `friendships` (requester_id, addressee_id, status smallint, UNIQUE(LEAST,GREATEST)); `groups`; `group_members` (PK(group_id,user_id), role smallint); `group_discussions` (media_id NULL FK, UNIQUE(group_id, media_id) WHERE media_id IS NOT NULL); `discussion_posts` (body varchar(1000)).

### Согласованность кода

- `z.string().uuid()` → `z.coerce.number().int().positive()` (`discussions`, `friendships`, `groups` schema).
- Роуты `[id]`/`[media]` парсят сегмент в число; невалидный — 400.
- `::uuid`/`::uuid[]` касты заменяются на числовые (`activity/repository.ts`, `groups/repository.ts`).
- Курсор ленты: id в base64url как число (`activity/domain.ts` и клиентская копия `movie-tracker/feed.ts`).
- `next-auth.d.ts` `uid?/user.id?` → `number`; `auth.ts` проверка `typeof token.uid === 'number'`.
- `row.user_id.slice(0, 8)` fallback handle → `String(row.user_id)`.
- Все пользовательские тексты: zod `.max(1000)` + CHECK в БД.

### Переписывание миграций

12 существующих миграций заменяются набором: `0000_init` (без pgcrypto), `0001_users`, `0002_media_and_genres`, `0003_ratings`, `0004_friendships`, `0005_groups_and_tags`, `0006_group_discussions`, `0007_discussion_posts`, `0008_activity_events`. Обратимость (`down`) сохраняется; `tests/integration/migrations.test.ts` обновляется.

## Risks / Trade-offs

- [bigint приходит строкой из `pg`] → единый `setTypeParser(20, Number)` в `core/db`, покрыть integration-тестом, что id — число.
- [Общая таблица `ratings` ломает границы модулей] → новый модуль `ratings` как единственный владелец; проверить `npm run deps:check` (правило `no-cross-module-repository`).
- [Клиентская копия курсора] → синхронизировать формат в `activity/domain.ts` и `movie-tracker/feed.ts`; unit-тест на round-trip.
- [Массивы `smallint[]` без FK] → коды задаются фиксированно в seed/справочнике, покрываются CHECK; повреждённые коды отсекаются при чтении.
- [Смена id на число влияет на сессию] → пользователи в seed фиксированы, `uid` число; проверить login/demo e2e.
- [Джойн оценки в ленте усложняет запрос] → индексы под keyset и по `(actor_id, media_id)`; тесты ленты.

## Migration Plan

1. Переписать миграции и `migrate`-совместимость; накатить на чистую БД (`db:migrate`).
2. Обновить `core/db` (парсер int8), модули, роуты, UI, `next-auth`, курсоры.
3. Переписать `scripts/seed-dev.ts`; выполнить `db:seed` на чистой БД.
4. Прогнать `lint`, `typecheck`, `deps:check`, unit, integration, `build`.
5. Откат: проект учебный — БД пересоздаётся с нуля; `down`-миграции сохранены для чистоты.
