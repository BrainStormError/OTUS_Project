## Context

См. `proposal.md` — Why. Текущее состояние:

- `users` (`..._users.sql`) хранит `name varchar(1000)` и `handle varchar(50)`; уникальность — частичный индекс `users_handle_key WHERE handle IS NOT NULL`. Поля `updated_at` есть, отдельных отметок времени смены нет.
- `deriveHandle()` (`src/modules/auth/repository.ts`) уже даёт нижний регистр `[a-z0-9-]` длиной ≤50 — новые правила формата соблюдаются, менять его не нужно.
- Запись аккаунта: `updatePrivacy` (`src/modules/auth/repository.ts`) и сервис `src/modules/auth/privacy.ts`; ручка `src/app/api/me/privacy/route.ts` через `withRoute` (`operation`, `schema`, `resolveActor`, `rateLimit`).
- `Actor` (`src/core/auth/policy.ts`) несёт `name`/`handle`; `getActor` кэшируется на запрос (`src/modules/auth/session.ts`).
- UI: `ProfileView.tsx` (свой/чужой профиль, флаг `isOwn`), `SettingsView.tsx` (секции темы/имени/приватности), `Modal` (`src/components/ui/modal.tsx`) с фокус-ловушкой и Escape.
- Регистрация ограничивает `name` 200 символами (`src/modules/auth/schema.ts`); существующие имена могут быть длиннее 100.

## Goals / Non-Goals

**Goals:**

- Дать пользователю менять своё отображаемое имя и тэг с описанными правилами.
- Единый серверный путь записи с валидацией, уникальностью и кулдауном тэга.
- Модальные окна и точки входа в профиле и Settings.

**Non-Goals:**

- Смена email, аватар, удаление аккаунта.
- Редактирование чужих аккаунтов и админский доступ к профилям.
- Изменение `deriveHandle` и логики регистрации.

## Decisions

### 1. Модуль и ручка

Сервис `updateIdentity` кладём в `src/modules/auth` (рядом с `privacy.ts`): обе сущности правят таблицу `users`, и это держит все мутации `/api/me/*` в одном модуле. Ручка — `PATCH /api/me/identity` через `withRoute` со схемой и `resolveActor` (только владелец аккаунта; актор берётся из сессии, id в теле не принимается).

- Почему: единообразие с `privacy`, одна точка авторизации.
- Альтернатива: сервис в `modules/profiles` — разрывает запись `users` между модулями; отклонено.

### 2. Валидация

Zod-схема `identityUpdateInput`: `name?` (trim, 1..100), `handle?` (trim, `^[a-z0-9_-]{1,50}$`, не `admin`/`root`), `.refine(хотя бы одно поле)`. Резерв-слова проверяются в схеме; уникальность — на уровне БД.

### 3. Уникальность и кулдаун

- Уникальность: предварительная проверка `findUserByHandle` для понятной ошибки + опора на `users_handle_key`; нарушение уникальности (pg `23505`) маппится в типизированный `CONFLICT`.
- Отправка текущего тэга — не изменение и не трогает кулдаун.
- Кулдаун: миграция `ALTER TABLE users ADD COLUMN handle_changed_at timestamptz` (nullable). При смене тэга `handle_changed_at` устанавливается в `now()`. Условие разрешения: `handle_changed_at IS NULL OR handle_changed_at <= now() - interval '1 month'`. Иначе — типизированный отказ с сообщением об остатке. Чтение пользователя и условный `UPDATE` выполняются в `withTransaction`, чтобы гонка не обошла кулдаун (обновление с `WHERE`-условием по времени, `rowCount = 0` → отказ).

### 4. Точки входа и модалки в UI

- Новый клиентский компонент модалки редактирования (переиспользует `Modal`, `Input`, `Button`) с обработкой ошибок полей: формат, reserved, занято, кулдаун.
- `ProfileView`: для `isOwn` рядом с именем и тэгом показываются кнопки-карандаши. Заголовок выносится в клиентский компонент `EditableIdentity`, который держит состояние модалок; для чужого профиля рендерится как есть.
- `SettingsView`: добавляются две кнопки «Изменить имя» и «Изменить тэг», открывающие те же модалки.
- После успеха — `router.refresh()`, чтобы шапка (`top-bar`) и профиль подхватили новые значения. Для своего профиля по адресу `/u/<handle>` после смены тэга выполняется переход на `/me` (старый адрес протухает).

## Risks / Trade-offs

- [Существующее имя >100 символов] → при сохранении пользователь обязан укоротить имя; документируем в UI-ошибке.
- [Гонка уникальности] → полагаемся на `23505` и маппим в `CONFLICT`, а не только на предпроверку.
- [`getActor` кэшируется на запрос] → новые значения видны со следующего запроса после `router.refresh()`; это ожидаемо.
- [Кулдаун «1 месяц» по rolling-интервалу] → используем `interval '1 month'`; календарный месяц не вводим.

## Migration Plan

- Миграция: `ALTER TABLE users ADD COLUMN handle_changed_at timestamptz;`. Существующие пользователи получают `NULL` → первая смена разрешена.
- Откат: удаление колонки; данные профиля не затрагиваются.
- Схема регистрации не меняется; новые правила применяются к правке профиля.
