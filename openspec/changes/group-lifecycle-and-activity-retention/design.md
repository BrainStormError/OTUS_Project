## Context

См. `proposal.md` — Why. Текущее состояние:

- `group_members` (`1710000000005_groups_and_tags.sql`) — состав группы; `removeGroupMember` (`service.ts:235`) блокирует только удаление/понижение **последнего** админа, самостоятельного удаления нет; выхода из группы нет.
- Удаление группы отсутствует. Каскады: `group_members`, `group_invitations`, `ratings.group_id`, `group_discussions` (+ `discussion_posts`) — `ON DELETE CASCADE`; `activity_events.group_id` — `ON DELETE SET NULL`.
- `AdminMemberPanel.tsx:76-94` — `invite()` оптимистично добавляет приглашение, кнопка остаётся «Пригласить»; повторные клики плодят дубли в списке.
- Лента: `listFeedEvents` (`activity/repository.ts:190`) листает все `activity_events` без ограничения по времени; планировщика очистки в проекте нет (`next start`, один контейнер).
- Профиль: `recent = entries = listPersonalRatings()` (`profiles/service.ts:37,51`); та же коллекция идёт в статистику.

## Goals / Non-Goals

**Goals:**

- Выход рядового участника, запрет самоисключения админа, роспуск группы администратором.
- Обратная связь по приглашению и запрет повторной заявки.
- Ограничение хранения ленты сутками и списка активности профиля неделей.

**Non-Goals:**

- Передача владения, публичные инвайт-ссылки, выход администратора без роспуска (сначала смена роли/роспуск).
- Новые таблицы или изменение каскадов БД.
- Дневной сброс ровно в полночь: используется скользящее окно 24 часа от текущего момента.

## Decisions

### 1. Выход из группы и запрет самоисключения

- Новый экшен `group:leave` (`policy.ts`): разрешён члену с `groupRole === 'member'`.
- Сервис `leaveGroup(actor, { groupId })`: отказ, если роли нет; отказ администратору (`FORBIDDEN`) — админ сначала меняет роль или распускает группу; иначе `deleteGroupMember(tx, groupId, actor.id)`.
- Ручка `DELETE /api/groups/[id]/membership` (действие над собой), в отличие от админской `DELETE /api/groups/[id]/members/[userId]`.
- Запрет самоисключения в `removeGroupMember`: если `input.userId === actor.id` → `FORBIDDEN`, даже когда есть второй админ.
- UI: `AdminMemberPanel` не рисует действие удаления для собственной строки; на странице группы рядовому участнику показывается кнопка «Покинуть группу».

Альтернатива — разрешить админу выходить при наличии второго админа — отклонена по требованию.

### 2. Роспуск группы

- Новый экшен `group:delete` (`policy.ts`, admin).
- Сервис `dissolveGroup(actor, { groupId })`: проверка права по `groupRole`; транзакция:
  1. `DELETE FROM activity_events WHERE group_id = $1` (новый repository-метод);
  2. `DELETE FROM groups WHERE id = $1` — каскад сносит участников, приглашения, оценки, обсуждения и посты.
- Ручка `DELETE /api/groups/[id]`; после успеха клиент уходит в `/groups`.
- Почему явное удаление событий до группы: `activity_events.group_id` — `ON DELETE SET NULL`, и без явного удаления события распущенной группы стали бы видны как личные/дружеские (см. `VIEWER_VISIBILITY` в `activity/repository.ts:77` и классификацию в `feed.ts:41,68`) — «фантомные» записи. Явное удаление согласуется с текстом спеки `groups/management`.
- Альтернатива — сменить FK `activity_events.group_id` на `CASCADE` — отклонена: лишняя миграция и изменение семантики для прочих потребителей.

### 3. Обратная связь по приглашению

- Локальное состояние `Set<inviteeId>` в `AdminMemberPanel`, инициализируемое из пропа `invitations` (server уже отдаёт pending), плюс добавление при клике.
- Кнопка для уже приглашённого — «Отправлено» с `disabled`; повторная отправка недоступна.
- Сервер не меняется: `upsertInvitation` уже гарантирует единственное pending на пару (группа, приглашённый).

### 4. Хранение активности — механизм B (ленивое удаление)

- Новый repository-метод `pruneStaleActivityEvents()`: `DELETE FROM activity_events WHERE created_at < now() - interval '1 day'`.
- Вызывается перед выборкой в `listFeedEvents` (главная лента) и `listGroupFeedEvents` (вкладка группы) — любое чтение ленты поддерживает таблицу ограниченной.
- Throttle: не чаще одного раза в минуту на процесс (in-memory отметка времени), чтобы не выполнять `DELETE` на каждый запрос при частых чтениях.
- Профиль: `buildProfile` фильтрует `recent` по `createdAt >= now - 7 дней`, статистика по-прежнему считается по всем `entries`. Оценки в БД не удаляются.
- Выбор `created_at`, а не `watched_at`: «активность» — это когда запись добавлена.

Альтернативы: `instrumentation.ts` + `setInterval` и `pg_cron` — отклонены (механизм B выбран пользователем; нет фонового процесса).

## Risks / Trade-offs

- [Запись на чтении ленты] → throttle раз в минуту; при малом масштабе приложения стоимость приемлема.
- [Глобальный дневной отсев затрагивает вкладку «Активность» группы] → вкладка тоже показывает только последние сутки; это принятое следствие и отмечено в proposal.
- [Роспуск необратим] → обязательное подтверждение в UI; явное удаление событий до удаления группы.
- [Клиенты SSE хранят уже удалённые события до реконнекта] → исчезнут после ближайшего рефреша/переподключения, лента не отдаёт устаревшее.
- [Потеря событий активности старше суток] → по замыслу; оценки, обсуждения и статистика не затрагиваются.

## Migration Plan

- Миграции БД не требуются: роспуск использует существующие каскады, отсев удаляет строки.
- Деплой: только код. Откат: возврат кода; удалённые события активности восстанавливаются только из бэкапа (осознанная потеря).
