# AI-Отчёт: жизнь проекта Movie Tracker

Дата отчёта: 2026-10-18. Источники: git-история (29 коммитов, 2026-10-04 — 2026-10-18), OpenSpec-изменения (51 шт., 46 заархивировано), ADR (5 шт.), `docs/01`–`docs/09`, README, инфраструктура (Docker, CI/CD, deploy-скрипты).

---

## 1. Что это за проект

**Movie Tracker** — сервис учёта просмотренных фильмов и сериалов: личные списки, «Буду смотреть», друзья, группы с общими оценками и обсуждениями, лента активности, каталог из TMDB.

- Стек: Next.js 16.3.8 (App Router), React 19.3, TypeScript strict, Tailwind 4, PostgreSQL 16, сырой `pg` без ORM, `zod`, Auth.js v5 beta.
- Архитектура: слои `app → modules → core` с автоматической проверкой границ (dependency-cruiser в CI).
- Масштаб на конец проекта: ~365 файлов TS/TSX, ~133 тестовых файла, 46 модулей API, деплой на VPS 1 vCPU / 1 ГБ RAM.
- Тесты: unit (Vitest), integration (Testcontainers с реальным PostgreSQL), e2e (Playwright). На момент последней большой проверки — 99 файлов / 732 теста.

## 2. Этапы жизни проекта

### Этап 0. Прототип UI (2026-10-04)
Начали не с кода, а с дизайна: спецификации экранов, светлая/тёмная темы (референсы — Calendly и Raycast), поиск, «Мои фильмы». Ещё до кода пересматривали UX дважды: убрали чекбокс-фильтры в пользу dropdown'ов, убрали двойной вход в поиск, сделали шаг рейтинга 0.5.

### Этап 1. Фундамент (2026-10-05 — 2026-10-07)
Bootstrap: слоистая архитектура, PostgreSQL через `pg` без ORM, `zod`-границы, Auth.js, CI с блокирующими проверками, `Result<T>` вместо try/catch-control-flow. Ключевые решения зафиксированы в ADR (см. раздел 4). Первая схема БД была сделана «на скорость» и через 2 дня переписана начисто (см. сбой №2).

### Этап 2. Настоящие данные и деплой (2026-10-10)
Один большой коммит «интеграция с TMDB, CI/CD, правки docker-compose», за ним 7 подряд коммитов исправлений: Dockerfile, размер образов, CI/CD (два раза), авторизация, загрузка постеров с TMDB. Это самый «пожарный» день проекта — см. сбои №3 и №4.

### Этап 3. Продуктовое наполнение (2026-10-11)
Один день — 13 коммитов и ~14 OpenSpec-изменений: поиск людей, профили из БД (не из моков), создание/управление группами, обсуждения и групповые оценки, лента активности, два прохода «security hardening», правки UI после ручного тестирования. Здесь же удалили демо-модуль `/directory` — эталонный вертикальный срез bootstrap перестал быть нужен.

### Этап 4. Социальные фичи + первая волна производительности (2026-10-12 — 2026-10-16)
Добавили watchlist («Буду смотреть»), тосты, дружбу, жизненный цикл групп, часовые пояса. Параллельно пошли жалобы на скорость: переходы 3–5 секунд, «зависания» без индикаторов. Появились скелетоны, `loading.tsx`, кэш каталога, streaming.

### Этап 5. Борьба за выживание на слабом VPS (2026-10-16 — 2026-10-18)
Хост — 1 ядро, 1 ГБ RAM, 2.5 ГБ swap, приложение в swap-thrash. Последние 8 коммитов — почти сплошь оптимизация: бюджеты памяти, статическая оболочка, отключение лишних префетчей, клиентский кэш, сериализация соединений с БД, постоянные (прогретые) подключения. Финальный коммит — «Ускорение работы с БД, добавление постоянных подключений».

## 3. Сбои и трудности: что происходило, как чинили, почему не видели сразу

### Сбой №1. Протокол безопасности: закрытые группы читал любой авторизованный
**Что было.** Аудит 2026-10-11 нашёл 6 дыр сразу: любой залогиненный пользователь мог по id прочитать участников, обсуждения и оценки закрытой группы; demo-вход позволял выдавать себя за другого и повышать себя до админа; сервер доверял клиентским метаданным (имя, жанры) при сохранении; тело запроса буферизовалось целиком (обход лимита через chunked — риск исчерпать память).
**Как чинили.** Единая точка авторизации `core/auth/policy.ts::can(...)`, роль читается из БД, закрытые группы наружу отдают 404 вместо 403 (не подтверждать существование), demo-вход запрещён в production и не даёт привилегий по email, лимит тела считается потоково в байтах.
**Почему не заметили изначально.** Авторизацию проверяли только на записях (мутациях), а чтения считались «безопасными по умолчанию». Плюс всё писалось на скорости руки в один день — ревью безопасности было отложено «на потом».
**Второй заход.** Уже на следующий день повторное ревью нашло ещё две серьёзные вещи: CI-деплой отключал проверку SSH host-key (MITM мог бы положить код в прод), а rate-limiter ключевался по `X-Forwarded-For`, который клиент может подделать, если прокси не перезаписывает заголовок. Исправлено: `StrictHostKeyChecking=yes` + fail-closed при пустом `DEPLOY_KNOWN_HOSTS`, доверие только к перезаписанному прокси заголовку (обязательная директива Caddy).

### Сбой №2. Схему БД переписали через 2 дня после создания
**Что было.** Первая схема (2026-10-05) накопила: uuid-ключи (16 байт вместо 8 у bigint), текстовые enum'ы, массивы `text[]` вместо связей, копии `title/year/genres` в каждой оценке, денормализованный `jsonb`-payload ленты. Следствия: события ленты ссылались на несуществующие оценки, у групп не было участников, лимиты не проверялись.
**Как чинили.** Полный реворк: 12 миграций переписаны в 9 (благо проект ещё не был в проде), `watched_records` + `group_ratings` слиты в одну таблицу `ratings` с nullable `group_id`, enum-текст → `smallint`-коды, события ленты — FK вместо jsonb-копий.
**Почему не заметили изначально.** Схему проектировали «на скорость» под прототип, без нормализации и без сценариев «событие ↔ оценка». Рассинхрон стал виден только когда наполнили схему реальными связями (seed отражал выдуманные данные).

### Сбой №3. Деплой изначально не мог работать
**Что было.** Остатки шаблона `birthday-platform` в именах образов и compose; CI триггерился на ветку `main`, а репозиторий живёт на `master` — проверки и деплой просто не запускались и никто этого не видел; migrate-контейнер не получал `DATABASE_URL`.
**Как чинили.** Переименование, перевод CI на `master`, отдельный migrator-образ, доставка образов на хост по SSH без реестра (`docker save | gzip | ssh`), deploy-скрипт с `save previous → migrate → up` и `trap`-откатом на предыдущий образ.
**Почему не заметили изначально.** CI, который не запускается, не выдаёт ошибку — он молчит. Молчаливый красный гейт хуже громкого.

### Сбой №4. TMDB: постеры, жанры, недоступность с РФ-VPS
**Что было.** Несколько проблем подряд:
- каталог был захардкожен (8 фильмов и 4 сериала);
- выпадашка жанров строилась из одной страницы «популярного» — большинство жанров было недостижимо, имена жанров зависели от живого вызова TMDB;
- multi-genre поиск делал AND вместо OR;
- жанровый фильтр на сериалах отдавал film-id (`series&genre=14`) — всегда пусто, потому что у TV-жанров другие id;
- постеры с TMDB не грузились (исправлено отдельным коммитом);
- с российского VPS `api.themoviedb.org` часто недоступен, а SSR ждал его до 5 секунд — страница висела целиком.
**Как чинили.** Полноценная интеграция TMDB v3 с хранением только оценённых тайтлов; словарь жанров синхронизируется в БД отдельным шагом деплоя (best-effort: падение TMDB не откатывает релиз); кэш TMDB вынесен в Postgres с TTL 6 часов и бюджетом по размеру; сервер больше не ждёт TMDB в пути запроса (streaming + fallback).
**Почему не заметили изначально.** Жанровые id TMDB для фильмов и сериалов — разные; в демо-каталоге этого не было видно. Медленный внешний API не проявляется на локальной машине с быстрым интернетом — вылез только на целевом VPS.

### Сбой №5. Медленная навигация: 3–5 секунд на переход
**Что было.** Каждый переход — полный SSR (`force-dynamic` из-за per-request CSP-нонса), без `loading.tsx`, без кэша переходов, без предзагрузки. Плюс шторм лишних запросов: на один переход навигационный шелл выпускал до 10 RSC-запросов (idle-прогрев всех 7 разделов + hover + focus + клик), постеры грузились без lazy и без резерва места (дёрганье вёрстки).
**Как чинили.** Эта проблема чинилась **четырежды**, с пересмотром решения каждый раз:
1. включили prefetch + `staleTimes` (10-16);
2. переделали prefetch «по намерению» + idle-прогрев (10-17);
3. полностью выключили prefetch шелла, убили прогрев («prefetch storm») (10-17);
4. финально: статическая оболочка (сняли `force-dynamic`, CSP на hash вместо nonce), дефолтный viewport-prefetch для 7 ссылок шелла, `staleTimes` подняты до суток, клиентские данные в общем сторе.
**Почему не заметили изначально.** `force-dynamic` с nonce-CSP запрещал любое кэширование по дизайну — на dev-машине это не раздражало. Лишние запросы маскировались быстрым локальным сервером и браузерным кэшем.

### Сбой №6. Рассинхрон данных в UI: «не видно без F5»
**Что было.** Отметил фильм на главной — в «Моих фильмах» его нет до перезагрузки. Кнопка «Буду смотреть» на карточках поиска **молча не работала**. После принятия заявки в друзья/группу UI не обновлялся. Оптимистичный стейт оставлял «призраков» при ошибке (например, DELETE вернул 502 — запись пропала из UI, но осталась в БД). 18 мест в коде вызывали `router.refresh()` как костыль.
**Как чинили.** Общий клиентский стор записей вместо независимых состояний на каждый экран, единый сигнал свежести. Важная находка: спайк показал, что в Next 16.3.8 `revalidatePath` из route handler **не сбрасывает** клиентский Router Cache — сигнал идёт только через ответ Server Action. Поэтому серверную инвалидацию, которую добавили как решение, потом удалили.
**Почему не заметили изначально.** Разные экраны держали независимый клиентский стейт и пустой RSC-снапшот переживал мутацию. Молча неработающая кнопка — худший класс дефекта: нет ни ошибки, ни теста, ни жалобы в лог.

### Сбой №7. Ошибки `timeout exceeded when trying to connect` — исчерпание пула БД
**Что было.** Один read-запрос держал до 3 соединений пула (`Promise.all` в `/api/friendships`, `/api/groups`, `/api/groups/[id]`), пул — 10 соединений с `idleTimeoutMillis: 30_000`. Бёрсты запросов вычитывали пул → продовые таймауты соединений. Браузер их **маскировал** своим кэшем, поэтому в UI всё выглядело нормально.
**Как чинили.** `Promise.all` → последовательные `await` (один запрос = одно соединение), переход на постоянные соединения (`min = max = 10` + прогрев при старте), таймаут ожидания 5 → 10 секунд. pgBouncer отвергли: LISTEN/NOTIFY требует session mode.
**Почему не заметили изначально.** Ошибки всплывали только под нагрузкой, а браузерный кэш чтений их скрывал. Плюс «один запрос — несколько соединений» неочевиден в коде с `Promise.all`, который выглядит невинно.

### Сбой №8. VPS в swap-thrash, Postgres жрёт CPU при простое
**Что было.** Хост 1 vCPU / 1 ГБ RAM: Node-heap рос бесконечно, логи без ротации, кэш TMDB без потолка (sweep раз в 5 минут детоастил до 100 МБ JSON прямо из пользовательского запроса!), Postgres со стандартными настройками. Замеры: `count(*)` по таблице в 11 строк — 250–360 мс, TTFB ~726 мс, `vmstat r = 7–12` при одном ядре (система почти целиком в очереди на диск), Postgres жёг 237% CPU при простое приложения. Отдельно: планировщик Postgres работал вслепую — `n_live_tup = 0` во всех таблицах, автовакуум не запускался.
**Как чинили.** Жёсткие бюджеты: heap 256 → 320 МБ, `shared_buffers` 64 → 128 МБ, `work_mem` 4 МБ, `max_connections` 20, `jit=off`, ротация логов 5 МБ/сервис. Бюджет кэша TMDB **пересмотрен вниз**: 100 МБ было больше, чем `shared_buffers` 64 МБ — рабочий набор никогда не помещался в память БД. Финальный бюджет — 16 МБ (14 МБ гистерезис). Sweep переведён на учёт `payload_bytes` вместо детоаста, проверка TTL без чтения payload. Вручную раскачаны статистики планировщика (`ANALYZE`).
**Почему не заметили изначально.** Бюджеты ставили «по ощущениям» (100 МБ кэша — круглое число), не сверяя с размером пулов памяти БД. Медленные холодные запросы на 11 строках выглядели как «глюк», пока не померили планы запросов.

### Сбой №9. Повторное сохранение и «двойной ввод»
**Что было.** Один и тот же тайтл можно было добавить повторно (модалки показывали весь каталог). Групповая и личная оценка сохранялись через две независимые формы — приходилось оценивать дважды. Отметка на главной не сохранялась (отдельный фикс), сохранение сериалов падало (отдельный фикс).
**Как чинили.** Уникальность записи, объединённая модалка оценки, фиксы сохранений — тремя отдельными коммитами 2026-10-12 и изменением `group-rating-dual-save`.
**Почему не заметили изначально.** Модальные формы строились от мокового каталога без проверок дублей; «двойной ввод» проектировали как две независимые фичи, не задумавшись, что пользователю это один сценарий.

### Сбой №10. Дубли запросов в группах
**Что было.** Переключение вкладки группы делало ~12 SQL-запросов, из них 8 — дубли: одна и та же группа загружалась 3–4 раза за рендер (`canViewGroup` вызывался в странице, в `getGroup` и в панелях).
**Как чинили.** Дедупликация запросов, клиентский стейт вкладок вместо полного SSR на клик, секционные скелетоны.
**Почему не заметили изначально.** Каждый слой (страница, сервис, панель) был «правильным» по отдельности; дубли видны только в сумме, на SQL-логе.

### Сбой №11. Уязвимости зависимостей загнали в угол
**Что было.** Блокирующий гейт `npm audit --audit-level=high` не проходил: база advisories помечает **все** версии Next.js < 16.3.8 как critical (RCE на Windows, SSRF, cache poisoning, XSS при CSP-nonce), патча в ветке 14 не существует. Пришлось поднимать весь стек: Next 14 → 16.3.8, React 18 → 19, next-auth v4 → Auth.js v5 beta, Tailwind 3 → 4, ESLint 9 flat config, `middleware.ts` → `proxy.ts`.
**Как чинили.** Апгрейд по решению заказчика (ADR 0004). Остаточный dev-advisory `braces` (тянется через `eslint-config-next`, апстрим-фикса нет) — гейт переведён на `npm audit --omit=dev --audit-level=high`: в production-дереве 0 уязвимостей (ADR 0005).
**Почему не заметили изначально.** Гейт поставили правильный, но стек выбрали старый «для стабильности» — эти два решения противоречили друг другу и столкнулись через неделю. Осознанно: вечно красный гейт начинают игнорировать, поэтому scope гейта сужен до production-дерева, а не отключён.

### Сбой №12. Часовые пояса, даты, мелкие UX-сбои
**Что было.** Даты постов обрезались (`post.createdAt.slice(0, 10)`) — UTC без времени, просмотр можно было датировать будущим числом, фильтр года работал по году релиза вместо года просмотра и выходил за границы календаря, кнопки вылезали из строк таблицы, privacy-тумблеры молча сбрасывались, dropdown жанров не закрывался, лента не скроллилась, после логина был редирект на уже удалённый `/directory`.
**Как чинили.** Пачкой изменений 2026-10-16 + спецификация timezone/time-format.
**Почему не заметили изначально.** Мелочи, которые видны только при ручном проходе по всем экранам; автотесты их не ловят по определению.

## 4. Решения, которые пересматривали (и почему это нормально)

| Решение | Сколько раз менялось | Итог |
|---|---|---|
| Стратегия префетча навигации | 4 разворота | Дефолтный viewport-prefetch для 7 ссылок шелла, свой прогрев — удалён навсегда |
| Серверная инвалидация (`revalidatePath`) | добавлена → удалена | Не работает из route handler в Next 16.3.8; свежесть несёт клиентский стор |
| Скелетоны загрузки | введены → отменены | Статическая оболочка делает их бессмысленными (осознанная отмена требования спеки) |
| `force-dynamic` + per-request CSP nonce | база → полный пересмотр | Hash-based CSP + статика + авторизация на уровне данных |
| Пул соединений БД | ленивый пул → постоянные соединения | `min=max=10`, прогрев при старте; pgBouncer отвергнут |
| Числовые бюджеты памяти | заморожены → пересмотрены по замерам | Кэш 100 → 16 МБ, shared_buffers 64 → 128 МБ |
| Схема БД | переписана целиком | 12 миграций → 9, bigint вместо uuid, слияние таблиц оценок |
| Per-episode оценки сериалов | введены → удалены | Убраны как избыточные при интеграции с TMDB |
| Стратегия кэша TMDB | in-memory → отвергнут `unstable_cache` → Postgres | TTL 6 ч, бюджет по байтам |
| Сырой `pg` без ORM | не менялся ни разу | Единственный фундаментальный выбор, который выдержал весь проект |

## 5. Выводы по жизни проекта

1. **Самые дорогие баги — молчащие.** Молча неработающая кнопка («Буду смотреть»), молча не запускающийся CI, маскируемые браузерным кэшем ошибки пула БД — всё это жило днями. Вывод: гейты должны падать громко, а контролы — подтверждать результат (тосты появились только 2026-10-16, когда проекту было уже почти 2 недели).

2. **Проблемы видны в сумме, а не в частях.** 12 SQL на клик при «правильном» коде каждого слоя; кэш в 100 МБ при `shared_buffers` 64 МБ; `Promise.all` из трёх запросов на пул из 10. Локально каждое решение разумно — дубли и конфликты бюджетов видно только на замерах целого запроса и на целевом железе.

3. **Dev-окружение врёт.** Быстрая машина и хороший интернет скрывали 3–5-секундные переходы, недоступность TMDB с РФ, swap-thrash на 1 ГБ. Всё, что важно, вскрылось только на реальном VPS. Вывод: бюджеты и замеры надо гонять на прод-подобном хосте с первого дня эксплуатации.

4. **Безопасность надо делать сразу и целиком.** Два подряд прохода hardening'а нашли 8 проблем (чтение закрытых групп, demo-impersonation, MITM в деплое, spoofable rate-limit и др.). Причина: авторизацию писали только для мутаций, чтения считали безопасными. Правило «каждый read тоже авторизуется» стоило двух дней работы и двух ревью.

5. **Решения имеют срок годности.** Префетч пересматривали 4 раза, скелетоны вводили и отменяли, бюджеты чинили по замерам дважды. Это не «метание»: менялось окружение (от dev-к VPS) и данные о системе (замеры TTFB, CPU, планов запросов). Нормально отказываться от своих решений — ненормально держать их из упрямства.

6. **Спайки дешевле интуиции.** Формальный спайк по `revalidatePath` в Next 16.3.8 (не сбрасывает Router Cache из route handler) сэкономил дни: решение добавили, проверили, **удалили**. Фраза из design-документа — «Spike 1.1» — показывает рабочий метод: гипотеза → замер → вывод, а не «надёжно сработает».

7. **Фундамент окупился.** ADR, слои с автоматической проверкой границ, `Result<T>`, fail-fast конфиг, пирамида тестов (732 теста) — именно это позволило потом делать крупные перестройки (реворк схемы БД, статическая оболочка, постоянные соединения) быстро и без страха. Единственный фундаментальный выбор, который не пришлось пересматривать за весь проект, — сырой `pg` без ORM.

8. **Технический долг копится незаметно и вылезает пачками.** 18 `router.refresh()`, денормализация jsonb в ленте, хардкод каталога, шаблонные имена `birthday-platform` — всё это «сделаем пока так», и всё это пришлось выбирать отдельными изменениями. Каждый отдельный случай был рационален; суммарная цена — примерно 4 из 46 изменений.

9. **Что осталось незакрытым.** Риск расхождения SQL↔типы (сырой `pg`, митигация только тестами, не codegen); dev-advisory `braces` без апстрим-фикса; e2e намеренно узкие (критичный путь требует живой БД); активные изменения (roles/moderation, cache invalidation) ещё не заархивированы; миграции в деплое откатываются вручную, не автоматически.

## 7. Почему в отчёте нет примеров промптов

Примеры промптов намеренно не приводятся: в этом проекте они сводятся к вызову OpenSpec CLI и skills (`openspec-propose`, `openspec-apply-change`, `openspec-update-change`, `openspec-archive-change` и др.), которые уже подробно описаны в своих документах и не нуждаются в дублировании. Вся идея взаимодействия с агентом проста и повторяется от изменения к изменению: объявить требования -> агент прорабатывает их через OpenSpec (proposal/design/tasks) -> согласование или не согласование плана агента. Реальная ценность проекта — в самих решениях, сбоях и выводах (разделы 2–6), а не в текстах промптов, которые одинаковы по форме и не несут дополнительной информации.
